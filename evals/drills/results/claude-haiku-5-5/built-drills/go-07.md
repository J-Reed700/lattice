## The key

### 1. Stale state (correctness.stale_state), Major, planted, search/filter.go lines 39 to 66

- Consequence: When a caller requests a page size above 100, the start offset is computed from the clamped size but the end index uses the original size, so the response returns more than the 100-item maximum and pages overlap, which breaks callers that paginate by page size.
- In an interview: The code reads the page size before it is clamped and uses that stale value for the end index, so the clamp is silently bypassed. Read the value once after clamping, or use q.PageSize consistently, so every calculation sees the same bounded size.

Proven by the judge: The edit saves the original PageSize into pageSize before clamping, then uses that unclamped copy for the end index while start still uses the clamped q.PageSize. The end index is computed from a stale copy taken before the clamp, so for requests above 100 the slice spans more than 100 items and pages overlap. The original code uses q.PageSize consistently for both start and end, so it does not have this mismatch.


The fix, in search/filter.go:

```diff
-	pageSize := q.PageSize
 	if q.PageSize > maxPageSize {
 		q.PageSize = maxPageSize
 	}
 
 	needle := strings.ToLower(strings.TrimSpace(q.Text))
 	matches := make([]Product, 0, len(products))
 	for _, p := range products {
 		if !matchesQuery(p, q, needle) {
 			continue
 		}
 		matches = append(matches, p)
 	}
 
 	switch q.SortBy {
 	case "price_asc":
 		sort.SliceStable(matches, func(i, j int) bool { return matches[i].PriceCts < matches[j].PriceCts })
 	case "price_desc":
 		sort.SliceStable(matches, func(i, j int) bool { return matches[i].PriceCts > matches[j].PriceCts })
 	case "name":
 		sort.SliceStable(matches, func(i, j int) bool { return matches[i].Name < matches[j].Name })
 	}
 
 	start := (q.Page - 1) * q.PageSize
 	if start < 0 || start >= len(matches) {
 		return []Product{}, nil
 	}
-	end := start + pageSize
+	end := start + q.PageSize
```

### 2. Integer overflow (correctness.integer_overflow), Major, found in review, search/filter.go lines 62 to 62

- Consequence: When Page is very large, (Page-1)*PageSize wraps around to a negative int. The start<0 check then returns an empty result with no error, so an invalid, absurdly large page number is silently treated as 'no results' instead of being rejected.
- In an interview: Multiplying an unbounded page number by the page size can overflow a fixed-width int, and the wrapped negative value is then caught by the empty-result branch rather than flagged. Checking the page against the match count before multiplying guarantees the product stays in range and that out-of-range pages still yield an empty page.

Proven by the judge: Overflow of (Page-1)*PageSize is a real edge case but a different problem from the stale page-size value; it does not name issue 1's cause.

The fix, in search/filter.go:

```diff
+	if (q.Page-1) > len(matches)/q.PageSize {
+		return []Product{}, nil
+	}
 	start := (q.Page - 1) * q.PageSize
```

- In an interview: An unrecognised SortBy is an invalid request, but the code treats it as a successful search and returns unsorted results. Validating the value up front and returning an error lets callers tell a bad request from a real empty or unordered result.

### 5. Stale state (correctness.stale_state), Major, found in review, search/filter.go lines 66 to 66

- Consequence: When a caller requests PageSize above 100, the offset is computed with the clamped size (100) but the window end uses the original, unclamped pageSize. Page 1 therefore returns up to the requested size instead of 100, and later pages overlap earlier ones or skip products.
- In an interview: The function clamps q.PageSize to maxPageSize but then uses a separate copy, pageSize, captured before the clamp, when it computes the end of the page. Pagination then mixes two different page sizes, so requests above the limit return oversized, overlapping pages, and the test suite misses it because it never sets a PageSize above 100.

Proven by the judge: Notes the test does not cover page sizes above the clamp, which would have caught issue 1, but it names test gaps rather than the clamp inconsistency as the cause.

The fix, in search/filter.go:

```diff

The claimed consequence is that if the goroutine panics before sending, the receive blocks forever. The missing-timeout pattern (a receive with no time limit) is technically present in the edited code, since the receive has no deadline, but the original code has no such blocking receive at all, so the edit does introduce a receive without a time limit. The specific claimed consequence (silent hang from a panic) is incorrect because the unrecovered panic terminates the process. ## The clean review

- Critical: The local slice `matches` in Search shadows the package-level function `matches`, so the call `matches(p, q, needle)` inside the loop tries to call a slice and the package does not compile. Renaming the function to `matchesQuery` resolves the conflict.
- Critical: The helper function is renamed to match its call site, removing the name clash with the local `matches` slice.
- Major: For large Page values, (q.Page-1)*q.PageSize can overflow int and become negative. The existing bounds check only tests start >= len(matches), so a negative start passes through and matches[start:end] panics. The check should also reject negative starts.
