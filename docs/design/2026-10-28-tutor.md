# The tutor

A chat that teaches from a course. It explains a subject from the course's sources, cites its claims, and
works the study methods into the conversation, so review happens while learning instead of in a separate
session the learner has to remember to open. Lessons, Practice, Quizzes and Recall stay as they are.

## 1. Decisions at a glance

| Question | Decision |
|---|---|
| What a tutor is | A chat conversation bound to one course (`conversations.program_id`), as an Explorer chat is bound to a folder. Same turn pipeline, same model picker, same tools. |
| What it adds to chat | The course as a source beside the library: search and read the course's sources, see its outline and the learner's progress, and read and write the course's recall cards and notebook. |
| How it plugs in | One port for "a source a chat reads beside the library", generalised from `ExplorerTurnPort`. The folder and the course are its two implementations. The turn pipeline changes only where it now holds a list of sources instead of one optional folder. |
| Where the study methods live | In the tutor's own prompt section and its tools, nowhere else. Other prompts are untouched. |
| How review stays real | Tutor questions on a recall card are rated into the same FSRS schedule the Recall tab uses, so a review in the tutor is a review. What the tutor teaches can become a card. |
| Which model | The chat's model, chosen like any chat's. The Learning model keeps building lessons. |
| Where it lives | A Tutor tab in the course workspace, listing the course's tutor chats. |
| Memory across chats | One rule for every harness: what the user says about themselves is shared with the chats bound to the same space, folder, course or lesson, and recalled before each turn only when relevant. |
| Evidence | The research and its limits are in [lessons built on learning science §2](2026-10-25-learning-science-lessons.md). This design applies the same findings to a conversation and claims nothing more. |

## 3. The design

### 3.1 One port for a source beside the chat

`ExplorerTurnPort` already describes a source beside the library: whether it has an index, the tools it adds,
the prompt block it contributes for a question, and how it runs its own tool calls. A course needs the same
four things. The port is renamed `TurnSourcePort` and kept as it is. A turn holds
`Vec<Arc<dyn TurnSourcePort>>` instead of `Option<ExplorerTurn>`, and the tool loop sends a call to the
source that offered the tool. `ChatRuntime::turn_sources(conversation_id, focus)` returns the conversation's
bindings: its folder, its course, or neither.

The course source is built in `features/learning` behind a core port and wired in `interfaces/di`, so no
feature reaches into another (`scripts/rust-architecture-check`).

One difference from the folder: a tutor must cite. Folder lines are cited by path and never numbered.
Course passages join the turn's numbered passages, as library passages do, so the chat's citation checks
apply to them unchanged.

### 3.2 What the course adds to the toolbelt

The tutor keeps every tool a chat has. The course adds:

| Tool | What it does | Built on |
|---|---|---|
| `search_course` | Passages from the course's sources for a query, labelled module › lesson › source | `CourseSearch` |
| `read_course_source` | A section of one source | course source versions |
| `course_outline` | Modules and lessons, which the learner finished, quiz results | learning repository |
| `due_reviews` | This course's cards that are due, fronts only | FSRS schedule |
| `record_recall` | Rates the learner's answer to a card into its schedule | `study_service::review` |
| `save_card` | Adds a card to the course deck with its citation | study cards |
| `save_note` | Saves the learner's summary to the Notebook | Notebook |

The model writes `record_recall` only for a card it asked from `due_reviews` or saved itself, and the rating
comes from the learner's answer, not the model's guess about it: the tutor asks how it went when the answer
alone does not settle it.

### 3.3 The study methods in a conversation

Each method from the in-app guide, how the tutor uses it, and what the harness gives it. The harness supplies
facts; the model decides how to say them.

| Method | In the tutor | From the harness |
|---|---|---|
| Retrieval practice | After teaching a point, a question the learner answers before the tutor moves on; the answer gets feedback that names the misconception, not only the right answer. A missed point becomes a card. | Each turn: turns since the last check. |
| Spaced practice | A session opens with the cards that are due, mixed into the conversation. Reviews here count in Recall: the Recall badge goes down. A test date on the deck pulls reviews in before it. | Each turn: cards due now. |
| Explain it simply | The tutor asks the learner to explain a point as to a beginner, then compares it with the cited passages and names what was missing. Gaps become cards. | The passages the point was taught from. |
| Interleaving and contrasting cases | Due reviews come from across modules. A new idea is set beside the earlier one it is easily confused with, naming the feature that differs. | The outline and what was covered recently. |
| Words with pictures | A diagram when an idea has structure, none decorative; `find_image` when a real picture helps. | Mermaid rendering, the image tool. |
| Notes in your own words | At the end of a stretch the learner writes the summary, the tutor points out what it left out, and it is saved to the Notebook. | `save_note`. |

As in lessons, the tutor asks for a committed answer before explaining when a newcomer would likely guess
wrong, and pitches questions so a learner who followed usually succeeds.

### 3.4 Memory shared by what a chat is bound to

Today a memory item is scoped to its conversation unless the user shares it, one item at a time, to its
space or to personal memory (`conversation_memory_attributes.scope`). Nothing is shared in practice. The
rule below is one rule for every harness: a conversation's memory scopes come from what it is bound to.

| Chat | Its scopes, narrowest first |
|---|---|
| Any chat | Its space |
| Explorer chat | Its folder, then each parent folder that has chats, then its space |
| Tutor chat | Its lesson (when opened from one), then its course, then its space |

| Rule | Decision |
|---|---|
| What is shared without being asked | What the user says about themselves: goals, preferences and facts about them ("interview on Friday", "explain with C# examples", "keeps mixing up `Task.Run` and `async`"). It goes to the conversation's narrowest scope. Instructions for one conversation ("no LINQ in this answer") and its decisions stay in it unless the user shares them. |
| How a shared item acts elsewhere | As context chosen by relevance, never as a mandatory item. Only a conversation's own constraints, goals and decisions are in every prompt, so one stray instruction cannot bind every chat in a course or folder. |
| What a conversation sees | Its own items, then each of its scopes in order, then personal memory. Never a scope it is not in. |
| Corrections and forgetting | A correction in any conversation supersedes the shared item everywhere; the superseding item inherits its scope, as `trg_memory_scope_superseded` already does. Forgetting removes it everywhere. Every item keeps its source conversation and exact quote. |

The scope chain is worked out in one place, from the bindings that `ChatRuntime::turn_sources` reads, so a
new kind of chat adds its scope there and nowhere else.

**What memory costs a turn.** Recall today searches the conversation's transcript on every turn (BM25 and
exact identifiers, no model call) and fills its whole budget with the best-ranked matches not already in
the prompt, with no relevance floor: "rename this variable" still brings in older passages that mention a
variable. Changed:

- The search still runs every turn, now over the shared items in the conversation's scopes as well; it is
  local and takes milliseconds.
- What it found joins the prompt only above a relevance floor, so an instruction with nothing relevant
  behind it adds nothing. The floor is set from the memory eval in both directions: questions answered
  only from memory are still answered, and instructions add next to nothing.
- The model is not told to search memory first: a tool call is a whole extra model round. The chat prompt
  says to use `search_saved_knowledge` only for something from before that is not already in front of it.
  Today no prompt mentions the tool; its description is all the model has.

### 3.5 Storage

- `conversations.program_id` and `conversations.lesson_id`, nullable, in a dated migration. A tutor chat
  is bound to a course and, when opened from a lesson, to that lesson. Deleting a course leaves its tutor
  chats as ordinary chats.
- `conversation_memory_attributes` replaces `scope` and `space_id` with `scope_kind` (`conversation`,
  `space`, `folder`, `course`, `lesson`, `personal`) and `scope_key` (the space id, canonical folder path,
  program id or lesson id), so a new kind of chat needs no migration. Existing space and personal rows are
  carried over. SQLite cannot alter a check, so the table is rebuilt in the migration.
- Nothing else: cards, reviews and notes go where Recall and the Notebook already keep them.

## 4. Evals

Run when the tutor's prompt, tools or the port change, on a synthetic course committed with the evals:

- Claims cite course passages, and the citation checks pass at the chat's rate.
- A teaching stretch reaches a retrieval question within a few turns; a session with due cards opens with
  them.
- A rated answer moves the card's FSRS schedule (read back from the database).
- Due reviews span modules.
- Non-tutor prompts are byte-for-byte unchanged, apart from the one line on when to search memory.
- The explorer's existing tests pass after the port is generalised.

New families in the conversation-memory eval, which also reruns as a whole first: it last ran on
2026-09-26, before #154, #157, #202 and this week's chat changes.

- A fact the user states in one chat is used in another chat with the same binding (space, folder,
  course, lesson), with its quote, and is absent from a chat outside it; a subfolder or lesson chat sees
  its parent's.
- An instruction with nothing relevant in memory adds next to nothing to the prompt.
- A correction in the second chat supersedes the item for the first; forgetting removes it from both.
- A shared instruction never becomes mandatory in a sibling chat.
- Questions whose answer is only in shared memory ("what did I say my interview date was?") are answered
  from it; guessing or saying it is unknown fails.
