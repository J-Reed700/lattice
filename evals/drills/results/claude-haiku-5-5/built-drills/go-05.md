## The key

### 1. Argument mutated in place (correctness.mutated_argument), Minor, planted, internal/upload/handler.go lines 73 to 74

- Consequence: The caller's multipart.FileHeader is rewritten, so any later code that reads fh.Filename (logging, auditing, a retry) sees a lowercased name that differs from what the client sent.
- In an interview: save mutates the FileHeader it receives instead of working on a local copy, which is a silent side effect on the caller's data. Compute the lowercased extension into a local variable and leave fh.Filename untouched.

Proven by the judge: The edit assigns the lowercased name back into fh.Filename, which is a field of the caller-supplied *multipart.FileHeader, so the caller's header is mutated in place. The original code only lowercased a local ext variable and never wrote to fh. The claimed consequence (later readers of fh.Filename see a lowercased name differing from the client's) is real for this edit. The edit introduces exactly the mutated-argument problem and the original lacks it.


The fix, in internal/upload/handler.go:

```diff
-	fh.Filename = strings.ToLower(fh.Filename)
-	ext := filepath.Ext(fh.Filename)
+	ext := strings.ToLower(filepath.Ext(fh.Filename))
```

### 2. Ignored error return value (errors.unchecked_return_value), Major, planted, internal/upload/handler.go lines 94 to 94

- Consequence: If the rewind fails, the copy starts from the wrong offset and the handler reports success, so a truncated or corrupt file is stored under a valid name.
- In an interview: The error from Seek is discarded, so the code proceeds as if the rewind worked. Check the error and return it, as the surrounding code does for every other I/O call.

Proven by the judge: The edit discards the error returned by src.Seek, so the unchecked return value pattern is introduced at that call. The original code checked the Seek error and returned it. However, the claimed consequence is overstated: a failed Seek on a multipart file (which is backed by an in-memory or temp file) is rare, and if it fails the io.Copy would still copy from the current position, possibly producing a truncated file, so the consequence (truncated file stored under valid name with success reported) is plausible in principle but the pattern itself is clearly the unchecked error. The original lacks this problem because it checks the error.


The fix, in internal/upload/handler.go:

```diff
-	src.Seek(0, io.SeekStart)
+	if _, err := src.Seek(0, io.SeekStart); err != nil {
+		return "", err
+	}
```

### 3. Leaked handle or connection (resources.leaked_handle), Major, planted, internal/upload/handler.go lines 84 to 84

- Consequence: Each upload that is rejected or fails during sniffing or copying leaves its source file open, and under load the process exhausts its file descriptors and starts failing requests.
- In an interview: The source handle is no longer closed on any return path, so the error returns in save leak it. Keep defer src.Close() directly after fh.Open so every path releases the handle.

Proven by the judge: The edit removes the defer src.Close(), so the multipart file source is never closed on any path in save. The original code closed src on every return path after fh.Open(), including sniff rejection and copy failure. The edited code therefore leaks the source handle on those error paths, matching the claimed consequence. However, fh.Open() for multipart files returns a sectionReadCloser over an in-memory or temp file; the leak is real for disk-backed temp files (large uploads exceed 1MB and are spooled to disk), so file descriptors can accumulate. The original code lacks the leak because the defer covers all paths.


The fix, in internal/upload/handler.go:

```diff
+	defer src.Close()
+
 	// Sniff the real type from the content, not the client-supplied header.
```

### 4. Partial update without rollback (errors.partial_update_without_rollback), Major, found in review, internal/upload/handler.go lines 53 to 65

- Consequence: When a later file in a multi-file upload fails validation or storage, the files already written stay in the upload directory while the client receives an error. A client that retries the whole batch stores duplicates, and the orphaned files accumulate with no record linking them to a request.
- In an interview: A batch upload that fails partway leaves the earlier files on disk even though the request is reported as failed, so the operation is only half applied. The fix is to validate every file before writing any, or to remove the files saved so far on each error path, as the replacement does with a small failure helper.

Proven by the judge: Points out that earlier files remain on disk when a later file fails. This is a real partial-write problem not in the key, and the code does leave saved files behind on error.

The fix, in internal/upload/handler.go:

```diff

+	}

 		name, err := h.save(fh)

-			http.Error(w, err.Error(), http.StatusUnsupportedMediaType)
+			fail(http.StatusUnsupportedMediaType, err.Error())
 			return
 		}
 		if err != nil {
-			http.Error(w, "could not store file", http.StatusInternalServerError)
+			fail(http.StatusInternalServerError, "could not store file")
 			return
 		}
 		saved = append(saved, name)
 	}
```

## The blind review

1. Major in internal/upload/handler.go: The opened multipart file `src` is never closed on any path. This leaks a file descriptor per uploaded file (multipart files may be spilled to disk). Add `defer src.Close()` right after the successful Open.
   Quoted: src, err := fh.Open() 	if err != nil { 		return "", err 	}
   Judged: Matches { issues: [2] }. Correctly identifies the unclosed src file leak on error paths, matching issue 2.
2. Major in internal/upload/handler.go: The error from Seek is ignored. If the rewind fails, the copy silently writes a truncated or wrong file. Check the error and return it.
   Quoted: src.Seek(0, io.SeekStart)
   Judged: Matches { issues: [1] }. Correctly identifies the ignored Seek error that can lead to a corrupt stored file, matching issue 1.
3. Major in internal/upload/handler.go: If a later file in the batch fails validation, earlier files were already written to disk and remain there while the client gets an error. Either validate all files before writing any, or remove the saved ones on failure.
   Quoted: for _, fh := range files { 		name, err := h.save(fh)
   Judged: ValidExtra. Points out that earlier files remain on disk when a later file fails. This is a real partial-write problem not in the key, and the code does leave saved files behind on error.
4. Minor in internal/upload/handler.go: The file is closed twice: once by the defer and once explicitly. The explicit Close's error is what matters for write durability, and it is correct here, but the deferred second Close is redundant and its error is discarded. Also, on copy failure the partially written file is removed while the deferred Close still runs, which is fine but easy to get wrong. Keep one close path, for example by closing explicitly and removing on any error.
   Quoted: defer dst.Close()  	if _, err := io.Copy(dst, src); err != nil { 		os.Remove(dst.Name()) 		return "", err 	} 	return name, dst.Close()
   Judged: FalsePositive. Says the double close is redundant and the explicit close error is correct; the finding is a style remark about the close path, not the leaked-handle issue of the key. The deferred close is harmless here, so it is a preference only.
5. Minor in internal/upload/handler.go: Every parse failure is reported as 413, including malformed bodies and wrong content types, which should be 400. Distinguish *http.MaxBytesError from other errors so clients get an accurate status.
   Quoted: if err := r.ParseMultipartForm(1 << 20); err != nil { 		http.Error(w, "request too large or malformed", http.StatusRequestEntityTooLarge)
   Judged: FalsePositive. Status-code choice for parse errors is a valid remark about accuracy, but it is not a real defect in the planted issues and is a judgement about API semantics rather than a defect of the key.
6. Nit in internal/upload/handler.go: The error text is returned to the client via err.Error(), exposing server-side sniffing details. It is minor, but the message format should be chosen deliberately rather than leaking internal classification.
   Quoted: return "", fmt.Errorf("%w: content is %s", ErrUnsupportedType, detected)
   Judged: FalsePositive. Exposing the sniffed content type in a client error is a minor information disclosure preference; the detected type is generic and not a real risk here.
7. Nit in internal/upload/handler.go: This mutates the caller's multipart header. Keeping the lowercased name in a local variable avoids surprising side effects on shared request state.
   Quoted: fh.Filename = strings.ToLower(fh.Filename)
