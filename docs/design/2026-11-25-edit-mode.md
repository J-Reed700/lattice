# Edit mode: one pipeline for correcting learning content in place

Date: 2026-11-25. Status: design, not built. Code read at `origin/main` `7ada090e3`;
the open branch `feat/lesson-prep-control-center-and-pipeline` (`264ade1ee`) was read for
every file this design touches, and nothing here depends on it.

## 1. Summary

A learner who sees an error in a lesson, a quiz question, a flashcard or a course outline switches
the application into edit mode and corrects the piece where it is shown. Today seven separate paths
edit such content, with five different stale-write checks, three history models and derived data
that each path updates by hand (§2). This design replaces them with one pipeline.

- **One address.** A piece of content is an entity of a registered kind, a field of it named by a
  JSON Pointer, and optionally a run of words in a text field (§3). Keys are the ones the
  application already stores.
- **One pipeline.** A change is a list of field operations against the revision the editor opened.
  `ContentEdits` loads the entity, compares the revision, applies and validates the operations,
  stores the result, records the change with its inverse, and runs the reactors, in one transaction
  (§6). A revert is the stored inverse through the same steps. An edit id makes a save repeatable.
- **One kind per content type.** A kind loads an entity as a document with a form of typed fields,
  checks the rules only it has, and stores a document (§3.2). Five kinds are registered at first:
  lesson section, quiz question, lesson, module, study card. Adding one is a registration.
- **One rule for jobs.** No job writes existing content. A job that derives content from what it
  read compares revisions before it publishes and starts again if the learner edited meanwhile. A
  model that wants text changed drafts a proposal that only the learner applies (§8).
- **One mechanism for derived data.** Reactors registered per kind update the claim ledger, the
  verification report, finding markers and quiz-bank status inside the edit's transaction, describe
  their effect before the save, and keep a receipt that a revert restores from (§9).
- **One editor.** A single dialog draws any kind's form, previews problems and consequences, shows
  both texts on a conflict, and lists the history with undo (§12). Edit mode itself is a view state
  that decides where Edit buttons are drawn.

The revision is a hash of the entity's content, so a stale save is refused whoever the other writer
was, and no content table gains a column (§7). Saves use an urgent lane in the write queue and stay
prompt while generation jobs write. The existing edit paths are deleted as they move onto the
pipeline, and three defects of their duplication close with them (§13). Quizzes already drawn and
grades already given are not changed by an edit (§10).

### 2.4 Writes under load

Every write waits in one first-come, first-served queue and holds no connection while it waits
(`lattice-core/src/shared/persistence/write_turns.rs:26-78`, `database.rs:48-60`). With thirteen
generation jobs running, a command's write waited behind the jobs' writes: one pause took 44 s to
land, and a pool acquire (5 s limit, one writer connection, eight readers:
`lattice-desktop/src/infrastructure/persistence/database/connection.rs:9-29`) timed out.

## 3. The model

The pipeline has four nouns. An *entity* is the unit that is loaded, checked for staleness, written
and reverted as a whole: one section, one question, one lesson, one module, one card. A *document* is
the entity's editable content as a JSON object. A *field* is a leaf of the document, named by a JSON
Pointer. A *fragment* is a range of text inside one text field. Everything a learner can point at is
an entity, a field of one, or a fragment of a field.

### 3.1 Addressing a piece of content

```
ContentRef     { kind: String, key: String }
ContentAddress { content: ContentRef, path: Option<String>, fragment: Option<TextSelector> }
TextSelector   { exact: String, prefix: Option<String>, suffix: Option<String>, start_byte: u32, end_byte: u32 }
```

- `kind` is a registered name of the form `<feature>.<noun>`, for example `learning.section`.
  `key` is the entity's key as the application already stores it; the kind defines its form
  (§3.2). No key is invented for this feature, and no key is derived from text.
- `path` is a JSON Pointer (RFC 6901) into the document: `/body`, `/choices/2/text`. The claim
  ledger already names fields this way without the leading slash (`options/1`, `rationales/0`,
  `rubric/2/description`), so a claim's location converts to an address by a rule the kind owns
  (`options/1` is `/choices/1/text`) and no table of names.
- `fragment` is a run of words in one text field, in the shape of a W3C Web Annotation
  TextQuoteSelector (`exact`, with optional `prefix` and `suffix`) refined by a position.
  `start_byte` and `end_byte` are UTF-8 byte offsets into the field's value at the revision the
  address was made for. The W3C TextPositionSelector counts characters; bytes are used here because
  every stored span in the application is a byte span (claim locations, saved passages) and because
  the exact source anchors planned for lesson citations are recorded in this shape. The two features
  share one type, `lattice_core::shared::text::selector::TextSelector`.
- A selector *holds* when the bytes at its position equal `exact`. One that does not hold is
  ignored: the editor opens the field with nothing selected. Nothing searches a field for the quote.
  The position is the address, and the quote is the proof that the address still names the same
  words. `prefix` and `suffix` are carried for the citation use and are not read by the edit
  pipeline. The editor converts between byte offsets and the UTF-16 offsets of its text control at
  the control.

Identity by position is kept where the application already has it: a section is
`(lesson_id, ordinal)`, the key of `learning_blocks` and the unit index of claims, teaching
findings, tangents and check drafts. That identity holds because nothing inserts, removes or
reorders the blocks of a published lesson one at a time, and this design adds no such operation
(§17). Preparing a lesson again replaces all of its blocks; that is a replacement of the content at
those keys, and the history treats it as one (§5.3).

A sentence, a worked-example step and a numbered item are not entities. They are text inside a
Markdown field, and Markdown has no node for a sentence. Addressing them as fragments keeps one
storage form for a section and still lets the learner point at the step. How a rendered step becomes
a fragment without matching text is in §12.3.

Rejected: an id per sentence or per list item. The ids would have to be written into the Markdown
or kept in a side table that every writer of `body` maintains, and generation, import and the
ledger's splices all write `body`.

### 3.2 Kinds and field descriptors

A kind is one implementation of `ContentKind` (§6.1) registered under its name. It loads an entity
as a document with a *form*, checks the rules only that kind has, and stores a changed document. The
form is a list of field descriptors, built per entity because it can depend on the entity (a check
section and a true/false question have different fields from their siblings):

```
FieldSpec =
  | Text   { path, label, format: line | plain | markdown, required }
  | Flag   { path, label, exclusive }        exclusive: at most one member of the enclosing list is set
  | Choice { path, label, options: [String] } the value is an index into options
  | Number { path, label, min, unit }
  | List   { path, label, item_label, min_items, max_items, item: [FieldSpec] }   item paths are relative
```

This is the schema-driven form pattern (JSON Schema with a UI schema, reduced to the five shapes the
content has). The editor surface draws any form; it has no code per kind. A full JSON Schema is not
used: the descriptors must also carry labels and the text format, and five variants are checked
exhaustively by the compiler on both sides of the IPC boundary.

Kinds registered in the first build:

| Kind | Key | Document | Notes |
|---|---|---|---|
| `learning.section` | `<lesson_id>/<ordinal>` | `/title` (line), `/body` (markdown), for every block kind | A check's question and answer are two ranges of `/body`, on either side of the one `### Check your thinking` line. The line is text in the body; the kind refuses a change after which a check that split no longer splits (`split_check`), so an edit cannot remove or repeat the line, and a check whose line is damaged can be repaired by editing it. Two fields for the halves were rejected: the form would change when a damaged check is repaired, so the edit could not be reloaded or reverted against one form, and the ledger reads a check's body as one field |
| `learning.question` | `<candidate_id>` | `/prompt` (markdown), `/explanation` (markdown). Single choice and multi-select add `/choices`, a list of `{text, correct, reason}`. True/false adds `/answer`, a choice of True or False, and `/reason` (plain, optional), why the other answer is wrong. Every other format offers `/prompt` and `/explanation` only in the first build (§10.1) | `correct` is exclusive for single choice. The key, the option order and the reasons array are composed from the document on store, so removing a choice cannot leave the key pointing at the wrong one. The composed question must pass `validate_candidate` |
| `learning.lesson` | `<lesson_id>` | `/title` (line), `/objective` (plain), `/estimatedMinutes` (number, min 1). The minutes field is left out for a lesson that is completed or has a started assessment | Stored through the curriculum snapshot (§13.4) |
| `learning.module` | `<module_id>` | `/title` (line), `/summary` (plain) | As above |
| `study.card` | `<card_id>` | `/question`, `/answer`, `/explanation` (markdown); a multiple-choice card has `/choices` of `{text, correct}` in place of `/answer`; a cloze card adds `/deletions`, a list of `{text}`; a code-prediction card adds `/language` (line) | Writes the recall profile and a version row when the card has a profile (§13.5). The fields follow the card's format and the format is not a field |

The list bounds are the ones the content already has, each with its purpose: 2 to 8 choices for
single choice and 4 to 6 with 2 to 3 correct for multi-select
(`assessment/assessment_engine/checks.rs:116-120`, `:239`), because every agreed bank item must pass
`validate_candidate` or no quiz in the course can start (`assessment_engine.rs:375-376`); at most 8
choices on a card, the range of `study_cards.correct_index`. No bound is added.

Adding a kind is: implement `ContentKind`, add it to the feature's `register` function, and wrap
the component that shows it (§12.2). Adding a field to a kind is a descriptor and the two lines that
read and write it.

### 3.3 Operations

A change is a list of operations on the document, a subset of JSON Patch (RFC 6902):

```
EditOp =
  | replace { path, value }    a leaf field takes a new value
  | add     { path, value }    a list gains a member at the index path names; "/choices/-" appends
  | remove  { path }           a list loses a member
```

`test` is not used; the entity revision (§7.1) is the precondition for the whole change. `copy` is
not needed, and `move` is a `remove` followed by an `add` in the same change, since no first-build
list carries meaning in its order.

A text field is always replaced whole. An edit of one step replaces `/body` with the body in which
that step's lines differ; the fragment says where the learner aimed and the operation says what the
field now holds. A splice operation (range and replacement) was rejected: it needs agreement on
offsets across UTF-8 and UTF-16 to apply, where the whole value needs none, and the server already
finds what changed inside a field by aligning sentences
(`claim_reviews/published_rewrite.rs`, `plan`). Text typed by the learner reaches the store
unmodified apart from line-ending normalisation (CRLF to LF, the form `published_rewrite::compared`
already compares in).

Operations apply to a copy of the loaded document by one function,
`apply_ops(document, form, ops) -> (document, inverse_ops)`. It refuses a path the form does not
describe, a value of the wrong shape and a list outside its bounds. It returns the inverse
operations in the order that undoes the change; the history stores them (§5).

### 3.4 Where a change comes from

```
EditSource = learner | proposal { proposal_id, model } | action { name }
EditOrigin = EditSource | revert { edit_id }
```

The source is recorded and has no effect on how the change is checked, applied or reverted. `learner`
is text typed in the editor. `action` is a button that stands for a fixed change, for example
"Remove this sentence" in claim review. `proposal` is a change a model drafted and the learner
accepted (§8.4). A revert is written by the pipeline itself. In W3C PROV terms the edit is the
Activity, the entity at its revision before and after are the Entities (`wasRevisionOf`), the
learner is the Agent, and a proposal is a Plan the activity used. The record keeps those four facts
and does not adopt the PROV vocabulary or serialisation, which would add a graph model for a log
with one agent.

## 4. Invariants

Each is enforced by construction in the place named, and has a test in §15.

1. **One writer.** A change to existing content of a registered kind is made by
   `ContentEdits::apply` or `apply_in` and by nothing else. Creating content (publishing a prepared
   lesson, importing a course, accepting a card draft) is not an edit. *Where:* the commands and
   functions of §2.2 are deleted, and the SQL that updates these columns moves into the kinds.
2. **One transaction.** The content rows, the edit record, the reactors' receipts and every
   reaction commit together or not at all. *Where:* `pipeline.rs`, one `WriteTx`.
3. **Revision-checked.** A change names the revision it was made against. If the entity is at
   another revision nothing is written and the caller gets `AppError::Conflict`. The revision is a
   hash of the document, so it also catches a writer that is not the pipeline.
4. **Reversible.** Every edit stores the operations that undo it. A revert applies them through
   the same pipeline and is itself an edit. An edit can be reverted while the entity's history from
   that edit to the present is unbroken (§5.3).
5. **The learner's text is not overwritten by a job.** No job writes a field of existing content.
   A job reads content at a revision; a job that derives new content from what it read compares the
   revision in its publishing transaction and starts again from the current text if it moved (§8). A
   job or model that wants existing text changed files a proposal, which only the learner applies.
6. **Structure is the application's.** Keys, ordinals, the index of the right answer, option
   order and the lengths of parallel arrays are composed by the kind from the document. No field
   lets them be typed and no model writes them. Structure that is a line of Markdown, the heading
   that divides a check, is guarded by the kind with the function the lesson reads it with.
7. **Derived data changes only in reactors.** A kind's `store` writes the entity's own rows. The
   ledger, the verification report, finding markers and anything else computed from the entity are
   written by reactors registered for the kind (§9).
8. **A copy is not rewritten.** A quiz form item, a practice session's prompt, a tangent's selected
   text and a card made from a lesson are records of what was shown or accepted. An edit to their
   origin leaves them as they are; the log lets a screen say the origin was corrected since (§9.3).
9. **An edit does not change a grade.** Item results, scores and evidence change only through the
   grade contest and override paths (§10.3).
10. **No decision reads wording.** Text is compared for equality or aligned by
    `lattice_core::shared::text::segmentation`; structure is read from Markdown block syntax, list
    markers and typed fields.
11. **Edit mode is a view state.** The backend has no notion of it. It decides where affordances
    are drawn and nothing else.
12. **An edit applies once.** The edit id is supplied by the caller; a repeat of the same request
    returns the recorded outcome.

## 5. Data model and migration

### 5.1 Tables

One migration, `crates/lattice-desktop/migrations/20261126000000_content_edits.sql`. No content
table changes.

```sql
CREATE TABLE content_edits (
    id TEXT PRIMARY KEY,
    kind TEXT NOT NULL,
    content_key TEXT NOT NULL,
    scope_feature TEXT NOT NULL,
    scope_container TEXT NOT NULL,
    seq INTEGER NOT NULL,
    origin_json TEXT NOT NULL,
    target_json TEXT,
    ops_json TEXT NOT NULL,
    inverse_json TEXT NOT NULL,
    before_revision TEXT NOT NULL,
    after_revision TEXT NOT NULL,
    reverts_edit_id TEXT REFERENCES content_edits(id) ON DELETE SET NULL,
    request_sha256 TEXT NOT NULL,
    outcome_json TEXT,
    app_version TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    UNIQUE(kind, content_key, seq)
) STRICT;
CREATE INDEX content_edits_by_scope
    ON content_edits(scope_feature, scope_container, created_at);

CREATE TABLE content_edit_receipts (
    edit_id TEXT NOT NULL REFERENCES content_edits(id) ON DELETE CASCADE,
    reactor TEXT NOT NULL,
    receipt_json TEXT NOT NULL,
    PRIMARY KEY(edit_id, reactor)
) STRICT;

CREATE TRIGGER content_edits_leave_with_their_course
AFTER DELETE ON learning_programs
BEGIN
    DELETE FROM content_edits WHERE scope_feature='learning' AND scope_container=OLD.id;
END;
CREATE TRIGGER content_edits_leave_with_their_deck
AFTER DELETE ON study_decks
BEGIN
    DELETE FROM content_edits WHERE scope_feature='study' AND scope_container=OLD.id;
END;
```

`seq` is the edit's position in its entity's history, from 1. `scope` is the container the entity
belongs to (a course, a deck): it is what a history list is filtered by and what the frontend's
invalidation is keyed on. The table is not tied to a content table by a foreign key because it is
shared by all kinds; the two triggers remove a container's history with the container, and a
feature that registers kinds later adds its own. `outcome_json` is the outcome returned for the
request whose id the row carries, kept so that a repeated request returns what the first returned
(invariant 12). It is null on the other rows one revert writes.

History is kept for as long as its container exists. A row holds a field's value twice (in the
operation and in its inverse); a section body is a few kilobytes, so no retention rule is needed
and none is added.

### 5.2 Why this history model

The history is a log of reversible patches: each row is the change and its inverse. The alternatives:

| Model | Taken or rejected | Reason |
|---|---|---|
| Reversible patch log (operations and their inverses, with before and after revisions) | Taken | The row says what changed in terms of fields and list members, which is what a history view shows and what a reactor needs. Revert is the stored inverse through the ordinary apply. Cost is proportional to what changed |
| Whole-entity snapshot per edit (as curriculum revisions and card versions do) | Rejected | It stores unchanged fields, and what changed has to be recomputed by a diff that cannot tell "choice 2 removed" from "choices 2 and 3 retyped". The two existing snapshot histories stay, as storage that belongs to their features (§13.4, §13.5) |
| Event sourcing (content is the fold of its events) | Rejected | Generation, import and publication write the content tables directly; making the log the source of truth would mean rewriting every writer and every reader. The claim ledger is event-sourced and stays so; it is a reactor's store, fed by this log's edits |
| Text diffs (unified diff or character operations) | Rejected | A diff applies only to the text it was made from, so revert after any other change needs fuzzy placement, a wording-dependent step that invariant 10 excludes. A stored diff format would also have to stay readable by every later build |

The content tables remain the source of truth, and the log is an audit and undo record beside them.
This is the split CQRS draws between the write model and what is read from it, without separate
stores.

### 5.3 The chain

Because every edit is revision-checked, an entity's rows form a chain: each row's `before_revision`
is the previous row's `after_revision`. The chain is *unbroken to the present* when the newest
row's `after_revision` equals the entity's current revision. It breaks when the content is replaced
instead of edited: a lesson prepared again from its outline, a card converted to another format, a
course imported over itself. Nothing has to notify the log when that happens. The revision is a hash
of the content, so the break is visible the next time the history is read.

- `revert(edit_id)` requires the chain from that edit to the present to be unbroken. It reverts
  that edit and, when the caller asks for it, every later edit of the same entity, newest first, in
  one transaction, each as its own row with `reverts_edit_id` set (§6.5). Undoing an undo is
  reverting the revert rows.
- Rows before a break stay as a record and are not revertible. The history view says the content
  was replaced after them. A replacement may reuse a key (a lesson prepared again has blocks at the
  same ordinals); the rows before the break then describe the content that key held earlier.
- `edited_paths(content)` returns the fields changed by edits in the unbroken part of the chain
  that have not been reverted. It is the question invariant 5 obliges a job to ask before it
  proposes a change to existing content.

## 6. The pipeline

### 6.1 Parts

The core is feature-agnostic and lives in `crates/lattice-core/src/shared/edits/`. It has no
knowledge of lessons, quizzes or cards.

```rust
#[async_trait]
pub trait ContentKind: Send + Sync {
    fn name(&self) -> &'static str;
    fn affects(&self) -> &'static [&'static str];
```

`Reading` is either unit of work borrowed to read from (new, beside `WriteTx` and `ReadTx` in
`shared/persistence/transactions.rs`, made with `tx.reading()`). The data-access rules let sqlx be
named only in data modules (rule 4, `scripts/rust-architecture-check/src/data_access/sqlx_types.rs`),
so a trait outside one cannot take a connection; `load`, `check` and `preview` run in a read unit
for a preview and in the write unit for a save, and `Reading` is the one type for both. It
dereferences to the connection as the two units do, under the same two exemptions of rule 5 they
have (`data_access.rs:72-96`). The SQL of a kind or a reactor stays in its feature's repository
modules.

`EditRegistry` holds kinds by name and reactors in registration order; a feature contributes both
through one `register(&mut EditRegistry)` function. `ContentEdits` is the service:

`context` is the one channel by which a feature's own command tells its own reactor why a change is
being made. Claim review uses it to say which statement a change edits, removes or restores (§13.3).
The pipeline hands it to the reactors and neither reads nor stores it; what a reactor needs later it
keeps in its receipt. It is a parameter of `apply_in` and not a field of the request, so the generic
command of §11 cannot carry one.

`apply_in` and `revert_in` return an `Uncommitted`: the outcome, and the follow-ups the reactors
asked for. The caller commits its unit and then passes it to `committed`, which runs the follow-ups
and returns the outcome. `apply` and `revert` do both themselves.

`marks` and `moved` are how a job keeps invariant 5: `marks` returns the revision of each entity a
job is about to read, and `moved` returns the entities whose revision differs from a mark or that
are gone (§8.2). `newest` returns, for each entity that has history, its newest edit, that edit's
origin, whether the chain is unbroken to the present, and one reactor's receipt for it; claim review
uses it to decide what its undo can take back (§13.3).

### 6.2 Applying a change

`apply` takes one write unit on the urgent lane (§7.3) and runs these steps. `apply_in` runs steps 2
to 11 in the caller's unit, for a command that must make a change and its own writes atomically, and
is the only entry that takes a `context`.

1. Begin the write unit.
2. If `content_edits` has a row with the request's `edit_id`: when its `request_sha256` matches,
   return the recorded outcome; otherwise fail with `InvalidInput`.
3. `kind.load`. No entity is `NotFound`. `not_now` is `InvalidState` with the kind's reason.
4. Compare `revision_of(document)` with `expected_revision`; a difference is `Conflict`.
5. `apply_ops` against the form. A refused operation is `InvalidInput`.
6. If the document is unchanged, return `changed: false` and write nothing.
7. Check the form's own rules (required text is not blank, a line holds no line break, list
   bounds, at most one exclusive flag), then `kind.check`. The first problem is `InvalidInput`
   carrying its message.
8. `kind.store`.
9. `kind.load` again. The stored document must equal the document from step 5, or the change fails
   with `InvalidState`; this is what makes the recorded `after_revision` the revision the next
   editor will be given, and it catches a kind that stores something other than what was checked.
10. Insert the `content_edits` row with the next `seq`.
11. For each reactor registered for the kind, in order: `apply`; store its receipt; collect its
    `affected` names with the kind's, its consequences and its follow-up. Record the outcome on the
    edit row.
12. Commit.

After the commit each reactor that returned a follow-up is given it (`after_commit`). A follow-up is
recomputation that needs units of work of its own, such as deciding again the statements of a kind
whose trust bar the edit moved (§9.2). It cannot undo the edit. A follow-up that fails is logged and
the save still reports success: the edit has two outcomes, applied or not, and none in between, and
the recomputation is one the next change of the same sort repeats.

The write unit contains only statements and in-memory work. No model call, no file access and no
network call is reachable from `load`, `check`, `store` or a reactor's `apply`; the data-access
rules already require every await inside a write unit to be a statement on it
(`scripts/rust-architecture-check/src/data_access/unit_of_work.rs`, rule 3(e)). Work a reactor
cannot do in a statement is a job it submits in the same unit with `JobStore::submit_in`
(`lattice-core/src/shared/runtime/jobs/repository.rs:232`). The pending row is the outbox, and the
dispatcher's poll finds it without a wake-up (`runtime.rs:284-286`). No first-build reactor submits
one.

### 6.3 Preview

`preview` runs steps 3 to 7 in a read unit, takes no write turn, and then asks each reactor for
consequences. It returns every problem (not only the first), the notices of §6.4, the consequences
and whether the revision still matches. A preview with no operations reports the notices of the
document as it stands. The editor calls it on open and after typing pauses, as the section
editor does today with its dry run (`LessonSectionEditor.tsx:60-81`), and shows the result under the
form before the learner saves.

A consequence is `{ code, message, related }`. The message is in plain words: "Saving changes 2
statements that were checked against the sources. What you write is marked as written by you, not
checked." `related` names other content the change leaves standing and the learner may want to open
next, for example the quiz questions that quote a sentence the edit removes (§9.2). Reactors write
consequences and the editor lists them; a saved edit returns the ones that were carried out.

### 6.4 Checks on Markdown

For a `markdown` field the core reports two notices, which inform and do not block:

- an ordered list whose markers do not count up by one ("The numbering jumps from 2 to 4 at line
  7. A line may have lost its number."), found with `segmentation::item_marker_end`
  (`shared/text/segmentation/prose.rs:125`) on lines outside code fences. Markers are compared
  within one list as CommonMark delimits it: items at the same indentation, up to a line that
  follows a blank line and is neither an item nor indented under one. A line without a marker that
  directly follows an item continues that item, so an item that lost its number does not end the
  list, and the marker after it shows the gap. A list whose items all carry the same number is left
  alone, since Markdown numbers it when it is drawn;
- a code fence that is never closed (`segmentation::code_fences`, `segmentation/fences.rs:30`,
  `closing: None`).

Both read list markers and fence lines, not wording. The first is how the misnumbered-items case
becomes visible in the editor (§14.4). The application does not renumber the learner's text: a
rewrite of marker lines the learner did not touch would change bytes under statements that were
checked.

### 6.5 Revert

`revert` takes `{ revert_id, edit_id, expected_revision, and_later }`. It loads the edit and every
later edit of the same entity, requires the chain to be unbroken to the present (§5.3) and the
caller's `expected_revision` to match, and applies each stored inverse through steps 5 to 11, newest
first, in one unit. When later edits exist and `and_later` is false it refuses with `InvalidState`
and writes nothing. The history view asks with `and_later: true` after listing what goes with the
edit; claim review's undo asks with `false` (§13.3).

The origin of each new row is `revert { edit_id }`. The row that reverts the newest edit takes
`revert_id` as its id, which is what makes a repeated revert return the recorded outcome (invariant
12). Each reactor is handed the receipt it wrote for the edit being reverted, so it can restore what
that edit ended instead of treating the restored text as newly written. `revert_in` does the same
inside a caller's unit. A revert never takes a `context`.

## 7. Concurrency

### 7.1 The revision

The revision of an entity is `sha256_hex` of the canonical JSON of its document (object keys sorted,
no insignificant white space), computed on load. It is a strong validator in the HTTP sense, and the
check is optimistic concurrency control: `expected_revision` plays `If-Match`.

A hash is used instead of a counter column for three reasons. It needs no column on five content
tables. It cannot drift from the content, where a counter moves only if every writer remembers to
move it; publication, import and any writer outside the pipeline are caught without cooperating.
And it is the one token for every kind, replacing the value comparison of sections and questions,
the ledger revision as an edit guard, the program revision for lesson titles and the card counter.
If content returns to an earlier value the hash matches again, and the save proceeds against text
that is the text the editor holds, which is correct.

The existing counters stay for what they guard. The ledger revision still orders ledger actions and
is bumped by the claims reactor, so a review screen holding an old ledger revision is refused its
next action as today. The program revision still guards plan revisions. The card counter still
numbers version rows.

### 7.2 A stale editor

On `Conflict` the editor keeps what was typed. It calls `open` again, shows the current content
beside the draft for each field that differs, and offers two actions: save the draft over the
current content (a new change made against the new revision), or discard the draft. There is no
automatic merge. A three-way merge of prose would be right only when the two changes do not touch
the same sentence, and the application has one user: the other writer is the same person in another
window or a rare outside write, and showing both texts is cheaper than explaining a merge.

### 7.3 Staying responsive under generation load

Three properties together keep a save prompt while jobs write.

**An urgent lane in the write queue.** `WriteTurns` gains a second semaphore. A standard writer
(`begin_write`, every caller today) takes the *lane* permit and then the *turn* permit, and holds
both until its unit ends. An urgent writer (`database.urgent().begin_write()`, new) takes only the
turn. The call is still named `begin_write`, which is how the data-access check recognises a write
unit, so the urgent unit is held to the same rules as any other. Standard writers therefore queue on the lane, and at most one of them is ever holding or
waiting for the turn; an urgent writer waits for at most that one unit, plus urgent writers ahead of
it. Among standard writers the order is unchanged, first come, first served. Urgent writers are a
person's clicks, so they cannot starve the lane. `apply` and `revert` use the urgent lane. Other
interactive commands can move to it one line at a time (§17).

The bound that remains is the longest single write unit of a job. The queue already logs every hold
over 100 ms with the place it began (`write_turns.rs:19`); a job unit that holds long is a defect of
that job and is fixed there.

**A short unit.** Steps 2 to 11 are a handful of keyed reads and writes on one lesson's rows.
Preview, where the sentence alignment and consequence counts are computed for display, runs in a
read unit: it takes no write turn and waits only for one of the eight reader connections.

**A save that can be asked again.** The edit id makes `apply` idempotent (invariant 12). If a save
fails with a pool timeout or the window closes while it waits, the editor still holds the draft and
the same id, and "Try again" either lands the change or returns the outcome that already landed. The
draft is also kept across a reload with the existing draft store (`src/shared/drafts/drafts.ts`).

Rejected: acknowledging the save at once and applying it later from a queue. The learner would see
text the database does not hold, a conflict would surface after the editor closed, and every reader
of the content would need to overlay pending edits.

## 8. Jobs, verification and the learner's edits

A job can do three things with content that exists: read it, derive new content from it, or want it
changed. Invariant 5 gives each one rule.

### 8.1 No job writes existing content

This is true of the code today and the design keeps it true by leaving no other writer.

| Job | What it writes | Existing content |
|---|---|---|
| Lesson preparation | Blocks, questions and the ledger of a lesson that is still an outline (`PREPARABLE_LESSON`) | None: a lesson with blocks is not preparable |
| Verification, audit, teaching check of a published lesson | Ledger events, the report, findings | Never `learning_blocks` or a question's text. A sentence the checker would take out of a published lesson becomes a finding or a proposal (§8.4) |
| Quiz bank | New candidates | None |
| Card and drill generation | New cards and drills | None |

Repair and rewriting during preparation act on a draft the job owns. `learning.section` and
`learning.question` report `not_now` for a lesson whose review is not `Ready` ("This lesson is still
being prepared. You can edit it once it is ready.", the text `section_edit.rs:33` uses today), so the
learner and the job never hold the same text. From publication on the text is the learner's.

A sentence the learner writes is recorded in the ledger as written by the learner and not checked
(§9.2). Verification does not rewrite or remove it. Whether a later audit may attach a verdict to it
is the ledger's existing rule for a user's statements, and this design does not change that rule.

### 8.2 A job that derives content compares what it read

A job that reads content, calls a model and publishes something derived from what it read can
publish from text the learner has corrected in the meantime. The quiz-bank lesson stage does this
today (§2.3). The rule is the read set of optimistic concurrency control:

```rust
pub struct ReadMark { pub content: ContentRef, pub revision: String }
```

1. In the unit that reads its inputs the job calls `ContentEdits::marks` for the entities it reads
   and keeps the marks in its checkpoint.
2. In the unit that publishes, before its first insert, it calls `ContentEdits::moved` with those
   marks.
3. If anything moved it publishes nothing, clears the checkpoint (`put_checkpoint` with
   `Value::Null`, `runtime.rs:167`) and runs the stage again from the current text.

The comparison is on the hash revision, so it also catches a lesson that was prepared again. The
stage repeats once per edit that lands while it runs; a person's edits are the only source of
repeats, so no retry count is set. The first build applies the rule to the quiz-bank lesson stage
(`assessment/quiz_bank_jobs.rs:311-409`): its marks are the lesson's `learning.lesson` entity and
each `learning.section` of it. The other jobs that read lesson text follow (§17).

### 8.3 Preparation and the outline

A change to a lesson's title, objective or minutes, or to a module, moves the outline revision
through the existing triggers, and a preparation job admitted under the earlier outline refuses to
publish (§2.3). The design keeps that rule: the titles and objectives of the course are inputs of
every lesson's generation. The `learning.outline` reactor adds the missing warning. Its `preview`
counts the course's preparation jobs that are pending or running and returns the consequence "3
lessons are being prepared from the outline as it is now. Saving stops them, and they will need to
be started again." An edit of a section or a question does not move the outline revision and stops
nothing.

A lesson prepared again is new content at the same keys. Its edit history ends at the replacement
(§5.3). The open branch's reset of a lesson is the same case and needs no hook: the reset deletes
the blocks, and the next read of the history finds the chain broken.

### 8.4 A model's proposal

A model that drafts a correction, whether a job found a problem or the learner described one,
produces a *proposal*: the content it is for, the revision it was drafted against, and the
operations. It is a `ContentEditRequest` without the decision to apply it. Only the learner applies
one, through the editor surface and `apply_content_edit`, with the source
`proposal { proposal_id, model }`. The pipeline treats that source as any other, so a proposal is
validated, applied, recorded, reacted to and undone by the code that handles a typed edit.

The first build contains the two parts of the seam that cost nothing: the `proposal` source in the
contract, and an editor that opens from supplied values (`initialValues`, §12.4) and saves with a
supplied source. The rest is a later package (§17):

- a table of proposals (`id`, content, `base_revision`, `ops_json`, the learner's description, the
  model, `pending | accepted | dismissed`, the edit that applied it);
- a drafting job. It opens the entity, gives the model the document, the form's text fields and the
  description, and takes back new values for named text fields through a schema whose keys are an
  enum of the form's text paths. The application builds the `replace` operations. The model writes
  no key, index or list structure (invariant 6);
- review in the editor surface: the proposal's values are the draft, shown against the current
  content with the comparison view of §7.2. A proposal whose `base_revision` no longer matches is a
  stale draft and is handled as one.

The drafting call goes through the Learning model's request layer and uses nothing a local model
lacks. A job that wants existing text changed files a proposal row in its own unit of work; it has no
other way to reach the text.

## 9. Derived data

### 9.1 One mechanism

Everything computed from an entity is updated by a reactor (§6.1) registered for the entity's kind.
A reactor runs inside the edit's transaction, after the content and the edit row are written and in
registration order. The mechanism has five parts, and each exists once:

| Part | Purpose |
|---|---|
| `preview` | What the change will do to derived data, in words, before the learner saves |
| `apply` | The derived writes, in the edit's transaction |
| receipt | What the reactor did, kept with the edit, so that a revert restores it |
| `affected` | The names of what the frontend holds and must read again (§12.5) |
| follow-up | Recomputation that needs its own units of work, after the commit |

In pattern terms a reactor is a synchronous handler of a domain event, run in the event's
transaction. Two other forms were rejected. Database triggers cannot align sentences, describe a
consequence or hand back a receipt; the triggers that move the outline revision stay, because they
state a fact in SQL and need none of that. An event bus that updates derived data after the commit
leaves a window in which a statement the learner rewrote still shows as checked, and a crash in
that window leaves it so. Work too long for a transaction is the exception, and it goes through the
outbox the job runtime already is (§6.2).

A feature registers its reactors in the same `register` function as its kinds, so adding a derived
store is one registration and no change to a kind.

### 9.2 Reactors in the first build

| Derived data | Kinds | Reactor | `apply` | Receipt |
|---|---|---|---|---|
| Claim ledger, verification report, teaching-finding marker, ledger revision, checker examples and trust calibration | `learning.section`, `learning.question` | `learning.claims` | Below | Events appended, claims created |
| Whether a bank question is used (`review_status`) | `learning.question` | `learning.quiz_bank` | A changed question that was `dropped` becomes `agreed`, the rule `claim_reviews/repository/questions.rs` (`write_question`) applies today | The status before |
| Bank questions written from a section's text | `learning.section` | `learning.quiz_bank` | Nothing is written. The consequence lists, as `related`, the lesson's bank questions whose `source_quote` occurred in the old text and does not occur in the new (exact containment) | None |
| Preparation jobs under the earlier outline | `learning.lesson`, `learning.module` | `learning.outline` | Nothing is written; the consequence of §8.3 | None |
| Duplicate suggestions | `study.card` | `study.duplicates` | `suggest_duplicates` again when the question changed | None |

Registration order for a section is `learning.claims`, then `learning.quiz_bank`.

Not reacted to, and why:

- **Search and embedding index.** Lesson text has none (§2.3). A kind whose content is indexed
  registers a reactor whose `apply` submits the re-index job with `JobStore::submit_in`; notes are
  the first such kind (§17).
- **Progress, completion, mastery evidence, card scheduling.** They record what the learner did,
  and a correction of the text does not change what was done. A corrected card keeps its due date
  and interval.
- **Read-aloud.** It synthesises from the text at the moment of the click.

**The claims reactor.** It is the one place that turns a change of a lesson unit's text into ledger
events. Its unit is the section's ordinal, or for a question the unit `FindingSite::Question` gives
the question's position among the lesson's own questions; a question the bank stage wrote has no
ledger unit and the reactor does nothing for it. A lesson without a review gets the finding marker
and nothing else. The reactor has three modes, chosen by what the change carries.

1. *A rewrite* (no context, not a revert): what `edit_section` and `edit_question` do today after
   their write. For each changed field it aligns old and new sentences
   (`published_rewrite::plan`), ends the statements whose sentence changed or went
   (`endings`, `record_edit`), records each new sentence as written by the learner and not checked,
   updates the report (`rewritten`), sets the finding marker (`mark_part_changed`), advances the
   ledger revision and settles what the ended statements give the checker examples and trust
   calibration. The kinds whose bar the settlement moved are the follow-up; `after_commit` decides
   those statements again (`redecide`), as `settled_revision` does today.
2. *A claim action* (context from claim review, §13.3): it records the action's event on the named
   statement and on the statements the change ends with it, updates the report with the step that
   action has today (`written_over`, `taken_out`, `taken_back`, `written_out`), sets the finding
   marker and advances the revision. The command that sent the context settles its own action, as
   it does today.
3. *A revert* (`reverted_receipt` present, and the reverted edit was not itself a revert): it
   appends `Undone { event_ordinal }` for every event the receipt lists, retires every claim the
   receipt says the edit created, brings the report to the restored text, sets the marker and
   advances the revision. This is what `published_restore::undo_in` does for one statement, driven
   by the receipt instead of by finding the sentence in the text. Reverting a revert is recorded as
   a rewrite (mode 1).

Its receipt is `{ "acted": [[claim_id, ordinal], …], "created": [claim_id, …], "step": string, "revert": bool }`.
Its `preview` returns the statement counts the section editor's dry run shows today, as one
consequence when a checked statement is affected (§6.3).

The finding marker is now set by every change of a unit's text, which closes the first defect of
§2.2: a sentence removed in claim review marks the teaching notes of its section as stale.

### 9.3 Copies

Four stores hold text copied from an entity at a moment: a quiz form's items, a practice session's
prompt, a tangent's selected text, and a card made from a lesson. They are records of what was
shown or accepted (invariant 8), and no reactor rewrites them. A screen that shows a copy can say
that its origin was corrected since: it asks `list_content_edits` for edits of the origin made after
the copy's creation time. The first build draws that note in one place, the review of a finished
quiz (§10.2). The others follow (§17).

## 10. Quiz content, forms and the existing reactions to a wrong item

### 10.1 The question kind

`learning.question` is keyed by the candidate id, the identity quizzes, forms, reports and grades
already use. The lesson editor's position-in-rowid-order identity is no longer an address. The one
place that still needs a position is the claims reactor, which derives it from the candidate id
(§9.2), so the mapping that was missing (third defect of §2.2) exists once and in one direction.

- `load` composes the document from the candidate and its answer key by format (§3.2). It reports
  `not_now` while the question is in a quiz the learner has open (a form whose status is `active` or
  `interrupted`): the document contains the right answer. The reason reads "This question is in a
  quiz you are taking. You can edit it when the quiz is finished."
- `check` composes the candidate the engine will read and runs `engine::validate_candidate`
  (`assessment_engine/checks.rs:241`), then compares the content token with the course's other
  questions ("Another question in this course has the same prompt and choices."). The blank and
  duplicate choice messages of `question_edit.rs:36-41` move here with their rule.
- `store` writes the candidate row, the answer key row and the content token
  (`assessment_repository/bank.rs:37`, `content_hash`). It does not touch `review_status` (§9.2).

Short answer, cloze, matching, ordering, explanation and artifact questions offer the prompt and
the explanation, which is what the lesson editor offers for them today. Their accepted answers,
pairs, order and rubric are typed structures that each need a descriptor of their own (§17);
`validate_candidate` still refuses a prompt edit that breaks one, for example a cloze prompt that
loses a blank its key names.

### 10.2 Forms

A form is a copy of its questions and of their key, taken when the quiz is drawn (§2.3). An edit of
a bank question changes neither. A quiz in progress keeps asking what it was drawn with, and a
finished quiz keeps the answers, key and grades it had. The tests that fix this
(`assessment_tests.rs:1379-1487`) stay as they are and gain one that makes the change through the
pipeline.

The review of a finished quiz is where a learner meets a wrong question, so in edit mode each
reviewed item carries the affordance for its bank question (the form item's id is the candidate id).
The editor's notes say "Quizzes you have already taken keep this question as it was asked." When the
bank question has edits newer than the form, the review says so under the item (§9.3).

### 10.3 Grades

An edit changes no result, score or evidence (invariant 9). A grade the learner disputes goes
through the paths that exist for it: the contest of a written answer and the override of a grade
(`assessment_repository/contests.rs:119`, `:301`). Correcting a wrong key therefore takes two steps
that are separate on purpose: the edit repairs the question for later quizzes, and the contest or
override repairs the grade already given. Folding the second into the first would regrade finished
quizzes as a side effect of fixing a typo in a choice.

### 10.4 Reporting

"Report this question" (`contests.rs:350`) stays. It removes a keyed question from later quizzes
without requiring the learner to know what is wrong with it. A reported question remains editable,
and the editor's notes say that it is left out of quizzes. Editing it does not put it back, which
is today's rule (`write_question` returns only a `dropped` question). Whether a correction should
return a reported question is a product decision (§17); the mechanism would be one more line in
the `learning.quiz_bank` reactor, with the receipt it already keeps.

The types as the frontend sees them (specta emits these from the Rust definitions in

## 12. Frontend architecture

The shared parts live in `src/shared/edits/` and know no kind. A feature contributes by wrapping the
components that show its content and by registering what its `affected` names mean.

### 12.1 The mode

Edit mode is one boolean in a store (`src/shared/edits/editMode.ts`). It is not persisted: the
application opens for reading, and the mode is entered for a correction. It is switched by a toggle
button (`aria-pressed`) in the Learning Studio page header, by a command-palette entry, and by a
registered shortcut (`global.editMode`, `Mod+Shift+E`, which a learner can rebind like any other).
While it is on, `RootLayout` shows a bar that says so and has a Done button, so the state is visible
on every screen, and a polite live region announces "Edit mode on. Each piece you can correct has an
Edit button." and "Edit mode off." Escape leaves the mode when no dialog is open.

The backend never learns the mode (invariant 11). Outside it, content looks and behaves as it does
today, with the per-section pencil removed. Claim review keeps its own actions in either mode,
because acting on a statement is that screen's purpose.

### 12.2 Marking what can be edited

```tsx
<Editable content={{ kind: 'learning.section', key: `${lesson.id}/${index}` }}
          path="/body" source={block.body} label={`section ${index + 1}: ${block.title}`}>
  <CitedSection … />
</Editable>
```

Outside edit mode `Editable` renders its children and nothing else. In edit mode it adds an outline
and a real button, "Edit section 3: <title>", in the tab order, placed before the content it
edits. Activating the button opens the editor on the entity. A pointer click on a rendered block
inside the wrapper opens the editor aimed at that block (§12.3). `path`, `source` and `sourceStart`
are optional and only serve that aim. Adding a kind to the frontend is wrapping the component that shows it.

First-build wrapping, each replacing an existing surface of §2.2:

| Shown by | Content | Replaces |
|---|---|---|
| `lessons/LessonCard.tsx`: lesson heading and objective | `learning.lesson` | The plan panel's lesson dialog (`curriculum/PlanPanel.tsx:187`) |
| `lessons/LessonCard.tsx`: each section; `lessons/active/LessonCheck.tsx`: a check's question and its answer, each a range of `/body` | `learning.section` | The pencil and `edit/LessonSectionEditor.tsx` |
| `curriculum/CourseSyllabus.tsx`: module title and summary, lesson rows | `learning.module`, `learning.lesson` | Nothing; module editing is new |
| `lessons/review/ClaimReviewScreen.tsx`: the unit a statement stands in | `learning.section`, `learning.question` | Both dialogs mounted at `:378-379`, and `edit/LessonQuestionEditor.tsx` |
| `quizzes/QuizItemReview.tsx`: a reviewed item | `learning.question` | Nothing; a form item could only be reported |
| `recall/flashcards/FlashcardDeckView.tsx`, `memory/MemoryPanels.tsx`, `recall/RecallEvolutionPanel.tsx`: a card | `study.card` | `EditFlashcard.tsx` and the two inline editors |

A recap that is held back until the learner has recalled the lesson is not wrapped while it is
held, as it has no pencil today. A statement the checker flagged is reached in two ways. Its
`ClaimLocationDto` and each `TeachingFindingDto` gain `address: ContentAddress | null`, made by
the backend from the location and its byte span, and "Edit the section" in
`UnverifiedStatements.tsx` and in claim review opens the editor at that address. The one-sentence inputs of the claim actions
(`UnverifiedStatements.tsx:84`, `ClaimActions.tsx:97`) stay: their value is the argument of a ledger
action, not a field of an entity, and the action reaches the text through the pipeline (§13.3).

### 12.3 From a rendered block to a place in the source

The viewer draws Markdown through markdown-it, whose block tokens carry the source lines they came
from (`token.map`). This is the source map used by synchronized Markdown previews, and CommonMark's
`sourcepos` is the same idea. A viewer-only Tiptap extension,
`src/components/TiptapEditor/extensions/sourceLines.ts`, keeps it:

- through tiptap-markdown's `parse.setup(md)` hook (the hook `extensions/math.ts:44` uses) it adds a
  markdown-it core rule that copies each block token's `map` into a `data-source-lines="a-b"`
  attribute;
- through a global attribute on paragraph, heading, list item, block quote and code block nodes it
  carries the attribute into the rendered DOM.

`Editable` reads the attribute of the nearest block under the pointer and opens the editor at the
field with an aim, `{ lines: [a, b], source, sourceStart }`. `source` is the text the viewer drew and
`sourceStart` the offset at which it stands in the field's value: 0 when the whole field was drawn,
and the start of the answer when a check's answer is drawn on its own. The editor turns the lines
into a `TextSelector` over the field's opened value and selects that range, only when the opened
value holds `source` at `sourceStart`. If it does not, the screen was showing other text than the
store holds, and the editor opens with nothing selected.

Nothing in this path compares wording: the address is a line range made by the parser from the text
it parsed, and one string equality decides whether it still applies. The grain is the block: a
paragraph, a heading, a list item (which is what a worked-example step and a numbered practice item
are), a code block. A sentence inside a paragraph is addressed only where the backend already has
its span, which is a claim's location. Aiming is a pointer convenience. The same edit is reachable
from the keyboard through the Edit button and the caret, so no function depends on the pointer.

### 12.4 The editor surface

One component, `ContentEditor`, mounted once by `RootLayout` and opened through the store
(`openEditor(address, options)`). It is a dialog built on `src/components/ui/dialog.tsx`: focus is
trapped while it is open and returns to the button that opened it. It has no code per kind.

- **Form.** It calls `open_content_edit` and draws the form with one control per `FieldSpec` variant
  (an exhaustive switch). `line` is a one-line input, `plain` a text area, `markdown` a text area
  over the Markdown source with the rendered result beside it. Markdown is edited as source because
  a rich-text round trip through the Markdown serialiser rewrites bytes the learner did not touch
  (list markers, emphasis characters, blank lines), and every rewritten sentence would end the
  statements checked on it. A list draws its items with Add and Remove buttons that respect the
  bounds. Each control has a visible label from the descriptor.
- **Operations.** `diffDocument(form, opened, draft)` produces the operations: a `replace` for each
  leaf that differs (two texts that differ only in CRLF against LF do not differ); for a list, a `remove` for each opened member that is gone (highest index
  first), then a `replace` for each changed field of a kept member at its new index, then an `add`
  at `/-` for each new member.
- **Preview.** When typing pauses it calls `preview_content_edit` and shows problems at their fields
  (`aria-describedby`, announced), notices under the field, and consequences above the Save button,
  each `related` item as a button that opens that content in the editor after this one closes.
- **Save.** `apply_content_edit` with an edit id made when the draft first differs and kept until
  the save succeeds, so "Try again" repeats the same request (§7.3). On success the editor closes,
  announces "Saved." with an Undo button in the announcement's toast, and refreshes what
  `affected` names (§12.5).
- **Conflict.** On `CONFLICT` it shows the comparison of §7.2.
- **Not now.** An entity that is `not_now` opens read-only with the reason in place of the Save
  button.
- **Draft.** The draft is kept with `src/shared/drafts/drafts.ts` under `edit:<kind>:<key>` as the
  opened revision, the values and the edit id, and is cleared on save or discard.
- **History.** A second tab lists the entity's edits from `get_content_edit_history`, newest
  first: when, where the change came from, and each field's value before and after. Each
  revertible row has an Undo button. When `later` is not zero the button names what goes with it
  ("Undo this and 2 later changes") and reverts with `andLater: true`.
- **Supplied values.** `options.initialValues` and `options.editSource` open the editor on a draft
  it did not type, to be saved with that source, which is how a proposal is reviewed (§8.4).

### 12.5 Reading again what changed

An outcome carries `affected` names and the edit's scope. `src/shared/edits/affected.ts` holds one
registry from a name to a function that invalidates the queries behind it, and the editor calls it
for each name. Learning registers its names in one file, from the key helpers that already exist
(`src/features/learning/api/learningQueryKeys.ts`):

| Name | Returned for | Queries |
|---|---|---|
| `learning.program` | section, lesson, module | The course workspace |
| `learning.plan` | lesson, module | The plan and its revisions |
| `learning.claims` | section, question (claims reactor) | Claim review and the lesson evidence |
| `learning.quizzes` | question | The quiz overview and the lesson question |
| `learning.recall` | a card with a recall profile | Recall and memory |
| `study.decks` | card | The decks |

The three hand-kept key lists of §2.2 call the same registry, so the keys behind a name are written
once.

### 12.6 Accessibility

Every affordance is a button with a name that says what it edits; no function needs a pointer. The
mode's state is exposed (`aria-pressed`), visible on every screen and announced on change. The
dialog is labelled by the entity's label from the backend. Problems are tied to their fields and
announced when they appear, and the conflict view and the result of a save are announced. Focus
moves into the dialog on open and back to the opening button on close. The outline that marks
editable pieces does not rely on colour alone, since the button is always present.

### 13.1 What each path becomes

| 4 | Teaching-note sentences | As path 3, one `apply_in` per sentence in the command's unit | As path 3 |

What the deleted functions decided moves to one owner each: the sentence alignment and ledger
writes to the claims reactor, the field rules to the kinds, the stale check to the revision.

### 13.2 Sections and questions

`learning.section` reads and writes `learning_blocks` through `claim_reviews/repository/blocks.rs`.
Its scope is the lesson's course. It is `not_now` unless the lesson's review is `Ready` or the lesson
has none (§8.1). Its `check` carries the two rules `section_edit.rs` has (a section needs a title
and some text) and one more: a body that `split_check` (`lesson_rules.rs:32`) split before the
change must split after it ("Keep the \"### Check your thinking\" line once, with the question
above it and the answer below it."). `learning.question` is §10.1.

### 13.3 Claim review

Claim actions stay claim actions: they are decisions about statements, and five of them also change
text. For a published lesson each of those five (edit, remove, put back, restore the original, and
the removal of a teaching note's sentence) is split where it already has two halves:

1. *Plan.* With the existing pure functions (`located`, `without_sentence`, `insert_sentence`,
   `put_sentence`) the command computes the unit's new field value from the document that
   `open_in` returns in the command's unit.
2. *Apply.* It calls `ContentEdits::apply_in` with one `replace`, the source
   `action { name }` (`claim.edit`, `claim.remove`, `claim.put_back`, `claim.restore`,
   `teaching.remove_sentence`), the target address of the statement, and a context:

   ```rust
   enum ClaimsContext {
       Claim { claim_id: String, event: ClaimEvent },   // the action as claim review resolved it
       Sentence { sentence: String },                   // a note's sentence no statement stands on
   }
   ```

3. *Record.* The claims reactor (§9.2, mode 2) appends the events, updates the report and keeps the
   receipt. The command then settles and commits as today and calls `committed`.

A batch of actions is a sequence of `apply_in` calls in one unit; each sees the text the one before
left. The ledger revision still guards the command.

**Undo.** An undo that takes back a change of text is a revert of the edit that made it. For the
statement's unit the command asks `ContentEdits::newest`. If the unit's newest edit came from an
action, the chain is unbroken, and the claims receipt lists the statement's undo target
(`ClaimLedgerEntry::undo_target`), the command calls `revert_in` with `and_later: false`; the reactor
(mode 3) appends the `Undone` events. Otherwise the undo is refused in the words used today
("This section changed after that, so it can't be undone on its own. Edit the section to change it
back.", `published_edit.rs:25`). A batch undo reverts a unit's newest edits one after another while
each one's receipt lists only statements in the batch, and refuses the whole batch if a requested
statement is not reached. Whether Undo is offered on a statement (`undoable_in_published`,
`actions.rs:70`, `teaching_claims.rs:100`) is the same test, read from `newest` for the lesson's
units when the review is loaded.

Two things follow, both intended. An undo is last in, first out within a unit: a sentence removed
before another change of the same section is taken back after that change, or with it from the
history view. And an action taken before this design is built has no edit to revert, so it is
changed back by editing the section. `undo_in`, `Undoing`, `removal_of`, `removal_refusal`,
`put_at_junction` (`content_verification/put_text.rs:178`, used by nothing else) and the two
refusal texts only they use are deleted. New removals stop writing the neighbouring sentences into
`TextRemoved`; the variant stays readable for the events already stored.

A lesson that is not published keeps today's behaviour. Its draft belongs to the preparation job,
and claim actions there write ledger events that the job applies.

### 13.4 Lesson and module

`learning_lessons` and `learning_modules` are projections of the accepted curriculum snapshot
(§2.1). An edit that changed only the projection would be overwritten by the next accepted plan
revision, so the kind's `store` writes both, in the edit's transaction:

1. the one row of `learning_lessons` or `learning_modules` (the existing triggers move the outline
   revision);
2. a new accepted row in `learning_curriculum_revisions`: the current accepted snapshot with that
   lesson's or module's fields replaced, a new id, the next revision number, the earlier one as
   parent and marked `superseded`, `required_lesson_count` and `resume_lesson_id` carried over, and
   the reason "Corrected a lesson's title, objective or time." or "Corrected a module's title or
   summary." A course with no snapshot yet gets one first through the existing `seed_on`;
3. `learning_programs.revision` plus one, the counter that guards plan revisions. A draft plan
   revision built before the edit then fails acceptance with the existing "Program changed; reload
   and retry.", which is correct: it was drawn from the earlier titles.

The whole-plan `materialize` is not run; one row changed and step 9 of §6.2 proves the row equals
the document. The snapshot encodes its own id and number, so reverting to an earlier title makes a
new snapshot and does not collide with the unique snapshot hash. The module's `/summary` is the
snapshot's `purpose`.

`EditLesson` refuses a completed lesson and one with a started assessment. That rule protects the
shape of a plan the learner has acted on, and the kind keeps it for the field that is plan, the
minutes (§3.2). A title or an objective with an error in it stays correctable, as a completed
lesson's sections are. This relaxes today's rule and is listed as a product decision (§17).

### 13.5 Study cards

`study.card` is keyed by the card id; its scope is the deck. The document follows the card's format
(§3.2), read from the recall profile when the card has one and from `study_cards` otherwise. `check`
composes the recall content and runs `validate_content` (`recall/recall_content.rs`). `store` calls
one repository function that writes the card's text everywhere it is kept: `study_cards`
(`question`, `answer`, `options_json`, `correct_index`, `explanation`) and, when a profile exists,
the profile's `prompt_json` and `answer_json`, `content_revision` plus one and a
`learning_recall_card_versions` row whose reason is "Corrected in place." or, for a revert, "Undid a
correction." The format conversion in `store_card` (`recall_repository/cards.rs:14`) calls the same
function, so the statements that write a card's text exist once. That closes the second defect of
§2.2. Scheduling columns are not written.

A conversion to another format replaces the card's content and breaks its edit chain (§5.3).
`save_learning_recall_card` refuses a save of an existing card that keeps its format ("Edit this
card in place to change its text."), which keeps one path per kind of change.

### 13.6 The open branch

Nothing in this design needs `feat/lesson-prep-control-center-and-pipeline`. The migration sorts
after the newest migration of both lines. The kinds and reactors read tables and columns that are
the same on both. The two lines change some of the same files: the claim-review modules, the review
screen, the quiz item and flashcard components, the plan panel, `curriculum_repository`, and the
command registration files. Whichever merges second keeps the other's behaviour and applies its own
change again on top: for this design that is the deletions of §13.1, the wrapping of §12.2 and the
registration lines of §11.3. The branch's reset of a lesson needs no code from this design (§8.3).

## 14. The error cases, end to end

Five errors of the kinds found in prepared lessons, each followed through the design. In all of them
the learner has turned edit mode on in the lesson.

### 14.1 One sentence of wrong reasoning in an explanation

The learner clicks the paragraph. `Editable` opens `learning.section` `<lesson_id>/<ordinal>` at
`/body` with the paragraph's lines selected (§12.3), and the learner rewrites the sentence. The
preview reports no problem and one consequence: "Saving changes 1 statement that was checked against
the sources. What you write is marked as written by you, not checked." Save sends one `replace` of
`/body`.

In one transaction: the block row is written; the edit row records the operation, its inverse and
both revisions; the claims reactor ends the statement on the old sentence, records the new sentence
as the learner's, updates the report, marks the section's teaching notes as needing another look
and advances the ledger revision; the quiz-bank reactor finds any bank question whose source quote
was in the old text and is not in the new, and lists it as related, so the learner can open the
question next. The outline revision does not move and no job stops. The lesson, its evidence and
claim review are read again.

Undo, from the announcement or the History tab, reverts the edit: the body returns to its bytes, and
the reactor, from its receipt, appends `Undone` for the ended statement and retires the learner's, so
the original sentence is shown as checked again.

### 14.2 A contrast section that shows two failures and explains one

A sentence is missing. The learner opens the section and writes it where it belongs. The alignment
finds one sentence the old text did not have and no sentence changed or gone: nothing checked is
affected, the preview shows no consequence, and the new sentence is recorded as the learner's, not
checked. Everything else is as in §14.1. If the learner wants the new sentence checked against the
sources, that is claim review's existing action on the statement, and this design does not change
it.

### 14.3 A worked-example step that calls a valid option a mistake

The step is a list item. A click on it selects that item's lines in the source, and the learner
corrects the wording inside the item. The item's marker is untouched, so the list's structure is
unchanged, and the change is one changed sentence, as in §14.1. A step can also be removed or
added: both are edits of `/body`, and the numbering notice of §6.4 appears if the remaining markers
no longer count up.

### 14.4 Numbered practice items that are misnumbered

In the lessons read for this design the fault has one shape: an item's line has lost its marker,
so Markdown reads it as more text of the item above and draws the items after it one number low.
The source reads 1, 2, 3, an unnumbered line, 5. On open the editor previews the unchanged
document, so the notice is there before anything is typed: "The numbering jumps from 3 to 5 at line
7. A line may have lost its number." The learner puts the marker back or corrects the numbers in
the source, and the rendered result beside the text area shows the list as it will be drawn.

An item whose text did not change keeps its bytes apart from the marker, but the marker is inside
the first sentence of its item: the sentence splitter starts an item's first sentence at the marker
(`content_verification/repair/cut.rs:42-50` strips it for that reason), and the ledger finds a
statement by the bytes of its sentence (`published_edit::placed`). A statement that was checked on
a renumbered item therefore ends, and the item's sentence is recorded as the learner's, as in
§14.1. The preview says how many statements that is before the save, and an undo restores them. In
the lessons read for this design about one statement in thirty stands on a sentence that opens with
a number, so the case is real and the count is usually small.

Keeping such a statement would need the ledger to record that a statement's sentence moved without
its words changing. No ledger event says that today, and comparing sentences without their markers
would leave the statement standing on a quote the text no longer contains. It is a change to the
ledger and is listed as a follow-up (§17), with "Renumber this list" as an `action` edit through
the same pipeline. The application does not renumber by itself (§6.4).

### 14.5 Statements the checker flagged that the learner knows are right

No text is wrong, so there is nothing to edit. The learner confirms the statements in claim review
or from the list under the section, which is the ledger action that exists for this (`Confirm`,
with a note where the ledger requires one). It writes ledger events and no content, so it does not
pass through the edit pipeline and leaves no edit history; it is recorded and undone in the ledger,
as today. Edit mode's part is that it does not get in the way: the flagged statement's "Edit the
section" opens the editor at the statement (§12.2) only if the learner chooses to change the text.
If a learner rewrites a flagged sentence instead, that is §14.1, and the flag ends with the
statement it stood on.

## 16. Alternatives considered

Alternatives to one part are discussed where the part is: identity per sentence (§3.1), a full JSON
Schema (§3.2), a splice operation (§3.3), the history model (§5.2), a counter as the revision
(§7.1), merging (§7.2), a deferred write (§7.3), triggers and an event bus for derived data (§9.1).
These are the alternatives to the whole.

| Alternative | Why it was not taken |
|---|---|
| Keep the seven paths and unify only the frontend | The defects of §2.2 are in the backend: five stale checks, three histories and derived data updated by whichever path remembered to. One surface over seven behaviours would hide the differences and keep them |
| Edit in place in the rendered view (the viewer made editable) | Rich text saved through a Markdown serialiser rewrites the whole body, so untouched sentences change bytes and lose their checked statements (§12.4). It also covers only Markdown fields; a question's choices and a card's answer would still need a form |
| One generic content table holding every document | Every reader and every generation job would be rewritten to gain a uniform store. The kind's `load` and `store` give the pipeline a uniform view and leave the tables as they are |
| Lock an entity while its editor is open | Jobs do not write existing content (§8.1), so there is nothing to lock against but the same learner's other window, and a lock left by a closed window needs an expiry, which is a number with no purpose to derive it from |
| Operational transformation or a CRDT for text | They merge concurrent writers. The application has one user, and §18 says what would change if it had more |
| A separate permission or backend state for edit mode | Edit mode is a place to draw affordances. A backend flag would be a second state to keep in step with the first and would protect nothing in a single-user application |
| Let a model apply its correction directly | Text the learner has not seen would replace text the learner relies on. A proposal costs one review and keeps one writer (§8.4) |

## 17. Out of scope and follow-ups

Out of scope, by decision:

- **Adding, removing or reordering sections.** Section identity is the ordinal (§3.1). An operation
  that shifts ordinals needs an identity that survives the shift for claims, findings, tangents and
  check drafts, and is a design of its own.
- **Changing a grade.** §10.3.
- **Editing sources.** A source version is evidence, not learning content.

Follow-ups, each an addition and none a change to the pipeline:

1. The proposal package (§8.4): the table, the drafting job, the review entry points.
2. Notes and memory as kinds, with the reactor that queues re-indexing (§9.2).
3. Read marks (§8.2) for the other jobs that derive content from lesson text: drills, card
   generation, practice.
4. Descriptors for the typed parts of the remaining question formats: accepted answers, cloze
   blanks, matching pairs, ordering, rubric (§10.1).
5. "Renumber this list" as an `action` edit, and a ledger event that lets a checked statement
   follow its sentence when only the list marker in front of it changed (§14.4).
6. The "corrected since" note on the other copies: practice prompts, tangents, cards made from a
   lesson (§9.3).
7. Moving other interactive commands to the urgent lane (§7.3), one command at a time, each with
   the measurement that justifies it.
8. On the open branch, the reset dialog can say how many of the learner's edits the reset replaces,
   from `list_content_edits`.

Product decisions the design takes a default on and that can be reversed without changing its
shape:

| Decision | Default here | The other choice |
|---|---|---|
| A title or objective of a completed lesson | Editable; the minutes are not (§13.4) | Keep today's rule and refuse, by returning `not_now` from the kind |
| A title or module edit while lessons are being prepared | Allowed, with the consequence shown first (§8.3) | `not_now` until the jobs finish |
| A corrected question that had been reported | Stays out of quizzes (§10.4) | The quiz-bank reactor returns it, with the status in its receipt |
| The per-section pencil outside edit mode | Removed; affordances belong to the mode (§12.1) | Keep it as a second entry to the same editor |
| Undo of a claim action in a section changed since | Refused; last in, first out (§13.3) | Offer "undo this and the later changes" in claim review, as the History tab does |
| Converting a card to another format | Stays a replacement that ends the card's undo chain (§13.5) | Model the format as a field, which needs a document that changes shape |

## 18. If content were shared

The application is single-user and local, and nothing here is built for more. This section records
which choices would hold if content were synchronised between devices or shared between people, and
which would have to change, so that the first build does not close the door by accident.

What holds:

- **The log.** Each row is a self-contained patch with the revision it applies to and the revision
  it produces. That is the unit a synchronisation protocol exchanges.
- **Hash revisions.** Two devices holding the same content compute the same revision without
  coordinating, which a counter cannot offer.
- **Field-level operations.** Two patches that touch different fields of an entity commute, so a
  merge could apply both; only two patches to the same text field need a person.
- **Reactors.** Derived data would be recomputed on each device from the patch it receives.
  Receipts describe local derived state and would stay local.

What would change:

- **Order.** `seq` assumes one writer per entity. Shared history needs an order that tolerates
  concurrent edits: a per-device counter with a causal parent in place of the single predecessor
  the before-revision names today.
- **Conflict.** §7.2 shows both texts because the other writer is the same person. With two people
  it needs a merge for the commuting case and attribution for the rest.
- **Who.** The origin records how a change was made. A shared log also records by whom: the Agent
  of §3.4 becomes a field.
- **Position as identity.** A section's ordinal is safe while nobody inserts a section. Shared
  editing makes insertion likely, which is the identity question of §17 again.
- **Claim actions.** A context is not stored (§6.1), so a device replaying a claim action's patch
  would record it as a rewrite. A shared ledger would exchange its own events.
- **Permission.** Edit mode stays a view state. Who may edit would be decided in the command layer
  and is unrelated to it.
