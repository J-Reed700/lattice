 9 | var (
10 | 	ErrNotRefundable = errors.New("capture is not refundable")
11 | 	ErrAmountTooHigh = errors.New("refund amount exceeds remaining balance")
12 | )
13 | 
14 | // Capture is a settled charge that refunds are drawn against.
15 | type Capture struct {
16 | 	ID             string
17 | 	AmountCents    int64
18 | 	RefundedCents  int64
19 | 	SettledAt      time.Time
20 | 	RefundWindow   time.Duration
21 | }
22 | 
23 | // Remaining returns how many cents can still be refunded from this capture.
24 | func (c Capture) Remaining() int64 {
25 | 	return c.AmountCents - c.RefundedCents
26 | }
27 | 
28 | // Plan computes the refund amount for a request. A zero requested amount means
29 | // a full refund of the remaining balance, which is how the storefront cancels
30 | // an order. Partial refunds must not exceed what is left on the capture, since
31 | // the processor rejects over-refunds and we would rather fail here with a
32 | // useful error than surface a processor decline to the customer.
33 | func Plan(c Capture, requestedCents int64, now time.Time) (int64, error) {
34 | 	if requestedCents < 0 {
35 | 		return 0, fmt.Errorf("refund %s: negative amount %d", c.ID, requestedCents)
36 | 	}
37 | 	if c.Remaining() <= 0 {
38 | 		return 0, fmt.Errorf("refund %s: %w", c.ID, ErrNotRefundable)
39 | 	}
40 | 
41 | 	// The window is enforced against settlement time, not the time the
42 | 	// customer asked, so clock skew at the edge cannot extend it.
43 | 	if c.RefundWindow > 0 && now.Sub(c.SettledAt) > c.RefundWindow {
44 | 		return 0, fmt.Errorf("refund %s: window closed at %s: %w",
45 | 			c.ID, c.SettledAt.Add(c.RefundWindow).Format(time.RFC3339), ErrNotRefundable)
46 | 	}
47 | 
48 | 	if requestedCents == 0 {
49 | 		return c.Remaining(), nil
50 | 	}
51 | 	if requestedCents > c.Remaining() {
52 | 		return 0, fmt.Errorf("refund %s: requested %d, remaining %d: %w",
53 | 			c.ID, requestedCents, c.Remaining(), ErrAmountTooHigh)
54 | 	}
55 | 	return requestedCents, nil
56 | }
57 | 
58 | // Total sums the refundable amounts across a batch of captures, skipping those
59 | // that cannot be refunded so a single closed window does not block a bulk run.
60 | func Total(captures []Capture, now time.Time) int64 {
61 | 	var sum int64
62 | 	for _, c := range captures {
63 | 		amt, _ := Plan(c, 0, now)
64 | 		sum += amt
65 | 	}
66 | 	return sum
67 | }

## The key

### 1. Missing null check (correctness.null_dereference), Minor, planted, payments/refund/refund_test.go lines 19 to 20

- Consequence: On the success path err is nil, so err.Error() panics and the full-refund test crashes with a nil pointer dereference instead of reporting a clear failure.
- In an interview: The check reads err.Error() before confirming err is non-nil, so a correct result makes the test dereference a nil interface and panic. The fix is to test err != nil first, or use t.Fatalf with err directly, so the nil case is never dereferenced.

Proven by the judge: The edit changes the success-path check to call err.Error() without first checking err for nil. On the success path Plan returns nil error, so err.Error() on a nil interface panics with a nil pointer dereference. The original code checked err != nil before using the result, so it did not have this defect. The edit introduces exactly the claimed null dereference in the test.


The fix, in payments/refund/refund_test.go:

```diff
 	got, err := Plan(c, 0, now)
-	if got != 4000 || err.Error() != "" {
+	if err != nil || got != 4000 {
```

### 2. Swallowed exception (errors.swallowed_exception), Minor, planted, payments/refund/refund.go lines 63 to 64

- Consequence: Any capture rejected by Plan is now silently counted with whatever amount Plan returns alongside the error, so a future change to Plan that returns a nonzero amount on error would inflate bulk refund totals without any signal.
- In an interview: The error from Plan is discarded, so the batch total no longer distinguishes a skipped capture from a refundable one. The fix is to keep the err check and continue on failure, so only explicitly valid amounts are summed.

Proven by the judge: The edit discards the error from Plan with a blank identifier and adds the returned amount to the sum unconditionally. This is a swallowed exception: failures are ignored and execution continues as if the operation succeeded. The claimed consequence is that a future Plan returning a nonzero amount alongside an error would inflate totals silently. Currently Plan returns 0 on every error path, so the immediate result is unchanged for the existing code, but the edit does introduce the swallowed-error pattern itself. The original code explicitly handled the error with continue, so it lacks the defect.


The fix, in payments/refund/refund.go:

```diff
-		amt, _ := Plan(c, 0, now)
+		amt, err := Plan(c, 0, now)
+		if err != nil {
+			continue
+		}
 		sum += amt
```

### 3. Untested branch (testing.untested_branch), Minor, found in review, payments/refund/refund_test.go lines 29 to 33

- Consequence: The negative-amount guard, the zero-window unlimited path and the exact window boundary are never run by any test, so a regression there, such as a flipped comparison or a removed guard, can let an invalid or out-of-window refund through to production without a failing test.
- In an interview: The test suite exercises only the happy path, an over-refund and one closed window, so the edge cases where money logic typically breaks go unverified. Adding cases for a negative amount, the exact window boundary and a zero window pins down the intended behaviour so a future change to the comparison or guards is caught immediately.

Proven by the judge: Points at missing test coverage (negative amounts, future settlement, window boundary). This is a real gap in the tests, not one of the planted issues, and it names a genuine risk in the money logic, so it is a valid extra.

## Dropped

- concurrency.check_then_act: The edit adds a duplicate copy of the same over-refund check immediately after the original one. The duplicate is redundant (dead code on the second evaluation, since the first return would already have fired), and it introduces no new concurrency behavior. The Plan function operates on a value copy of Capture and performs no shared-state check-then-act sequence in either version; the race described (two concurrent callers passing the balance check before recording a refund) would depend on the persistence layer, which is not shown and is unchanged by the edit. The original code already contains the same check-then-return pattern, so the claimed concurrency race is not introduced by this edit, and the claimed consequence (concurrent over-refunds) is not caused by the edit.
  Consequence claimed: Two concurrent refund requests against the same capture can each pass the remaining-balance check before either records its refund, so the combined refunds exceed the capture amount and the processor declines the second one.
