### 1. Unhandled boundary or empty input (correctness.boundary_and_empty_input), Minor, planted, internal/session/store.go lines 70 to 70

- Consequence: A session is still accepted at the exact instant of its ExpiresAt deadline, so a token can be used for one extra tick after expiry. It only shows up at the exact boundary, so it is rarely noticed.
- In an interview: The expiry check now treats the deadline instant as still valid, which is an off-by-one at the boundary. Expiry should use !now.Before(ExpiresAt), so that the session is dead at the deadline itself.

Proven by the judge: The original Lookup treats a session as expired when now is not before ExpiresAt, i.e., at the exact deadline it is rejected. The edit changes the check to now.After(ExpiresAt), which is true only strictly after the deadline, so at the exact instant ExpiresAt the session is accepted. This introduces the claimed boundary off-by-one at the exact deadline in Lookup. The original code does not have this problem since it rejects at equality. The edit's change is exactly the boundary behavior described, and the claimed consequence (one extra tick of acceptance at the exact expiry instant) follows directly. Note the Rotate path still uses the original check, but that is not a new issue introduced by the edit.


The fix, in internal/session/store.go:

```diff
-if s.now().After(sess.ExpiresAt) {
+if !s.now().Before(sess.ExpiresAt) {
```

### 2. Partial update without rollback (errors.partial_update_without_rollback), Major, planted, internal/session/store.go lines 82 to 96

- Consequence: Rotation is no longer atomic: if the process fails between creating the new session and revoking the old one, or two rotations of the same token race, both tokens stay valid and the fixated token survives the privilege change.
- In an interview: The rotation is split into a create step and a separate revoke step with no lock or compensation covering both, so a failure partway leaves two live sessions. Rotation should swap the token under a single lock (remove old and insert new in one critical section) so the change is all-or-nothing.

Proven by the judge: The original Rotate atomically removes the old token under the lock before creating the new one, so two concurrent rotations of the same token cannot both succeed, and the old token is gone before a new one exists. The edit reads the old token under lock, releases it, then creates the new session and only afterward revokes the old one. This introduces a window where two concurrent Rotate calls on the same token both succeed, yielding two valid fresh tokens, which matches the claimed race consequence. The claimed failure of a crash between create and revoke also becomes possible, leaving the old token valid. Thus the edit introduces the non-atomic rotation problem that the original lacked, since the original deleted under the same lock and had no such window.


The fix, in internal/session/store.go:

```diff

+		delete(s.sessions, token)

 		return Session{}, ErrSessionNotFound

 	}

-		return Session{}, err
```

### 4. Check-then-act race (concurrency.check_then_act), Major, found in review, internal/session/store.go lines 70 to 72

- Consequence: Lookup checks expiry under the read lock, then deletes under the write lock without rechecking. If another goroutine replaces the token's entry in that gap, the delete removes a fresh, valid session, which logs that user out unexpectedly and can surface as ErrSessionNotFound on a live token.
- In an interview: The expiry decision is made on a snapshot taken under the read lock, so it can be stale by the time the write lock is taken. Rechecking the current entry under the write lock before deleting ensures only the expired session is removed, never a replacement stored in the gap.

Proven by the judge: Describes a real race in Lookup where the expired-entry delete can remove a replacement session. This is a valid problem but not the boundary issue planted at line 70.

The fix, in internal/session/store.go:

```diff
 	if s.now().After(sess.ExpiresAt) {
 		s.mu.Lock()
-		delete(s.sessions, token)
+		if cur, ok := s.sessions[token]; ok && !s.now().Before(cur.ExpiresAt) {
+			delete(s.sessions, token)
+		}
```

### 5. Unbounded growth (resources.unbounded_growth), Minor, found in review, internal/session/store.go lines 88 to 90

- Consequence: When a client presents an expired token only to Rotate, the entry stays in the sessions map because the expired branch never deletes it. Abandoned sessions that are never looked up again accumulate, so memory use grows slowly over the life of the process.
- In an interview: Rotate returns ErrSessionExpired for an expired token without removing it, while Lookup deletes it, so expired entries can linger in the map. Calling Revoke on the expired path, which takes the lock itself and is safe because the lock is not held at that point, makes both paths evict stale sessions the same way.

Proven by the judge: Claims Rotate leaves expired entries in the map unlike Lookup. Rotate's expired path does not delete, which is a real inconsistency, so it is a valid extra with minor impact.

The fix, in internal/session/store.go:

```diff
 	if !s.now().Before(old.ExpiresAt) {
+		s.Revoke(token)
 		return Session{}, ErrSessionExpired
 	}
```

### 6. Unbounded growth (resources.unbounded_growth), Major, found in review, internal/session/store.go lines 55 to 57

- Consequence: Sessions that are created and never looked up again, such as from abandoned logins, stay in the map after they expire. Memory grows with every such session until the process is restarted or runs out of memory.
- In an interview: Expired entries are only removed when someone looks them up, so sessions that are never presented again accumulate forever. Sweeping expired entries on write bounds the map to the live sessions, though a sweep on every Create is O(n), so a production version would sweep on a timer or every N calls.

Proven by the judge: Points out that abandoned expired sessions are never swept, so memory grows without bound. This is a real risk in the store.

The fix, in internal/session/store.go:

```diff
 	s.mu.Lock()
+	now := s.now()
+	for k, v := range s.sessions {
+		if now.After(v.ExpiresAt) {
+			delete(s.sessions, k)
+		}
+	}
 	s.sessions[token] = sess
 	s.mu.Unlock()
```

## The clean review

- Major: Rotate is not atomic. It looks up the old token, creates a new session, and only then deletes the old token, with separate lock acquisitions. Two concurrent Rotate calls on the same token can both succeed, so one old token yields two valid sessions. This defeats the purpose of invalidating the old token. Claiming the old token under a single lock before creating the replacement closes the window.
