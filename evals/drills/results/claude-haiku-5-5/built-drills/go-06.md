## The key

### 1. Integer overflow (correctness.integer_overflow), Major, planted, notify/dispatcher.go lines 42 to 43

- Consequence: With a large maxAttempts the shift overflows the int64 Duration, so the initial delay becomes zero or negative and retries fire immediately or the timer misbehaves, with no error reported.
- In an interview: Scaling the Duration by a left shift of maxAttempts overflows int64 once the count is large, producing a wrong backoff value. Keep delay equal to baseDelay and let the doubling step grow it, with a cap if needed.

Proven by the judge: The edit changes the initial delay from baseDelay to baseDelay shifted left by maxAttempts. The shift is performed on a time.Duration (int64), so with a large maxAttempts (e.g., 64 or more, or enough that the shifted bits overflow the sign bit or the value wraps to zero) the initial delay can become zero or negative, which is the claimed consequence of integer overflow. However, the edit also changes behavior for ordinary values: with maxAttempts=3 and baseDelay=1ms the initial delay becomes 8ms, so the backoff schedule is wrong even without overflow, which is a different defect (incorrect delay scaling) rather than purely overflow. The edit does introduce a shift that can overflow for large maxAttempts, so the overflow pattern is present in the edited code, but it is accompanied by an unintended semantic change. The original code has no such shift and no overflow risk in the delay computation (delay *= 2 is only applied in the loop and is bounded by attempts in practice), so the original lacks the problem.


The fix, in notify/dispatcher.go:

```diff
-	delay := d.baseDelay << uint(d.maxAttempts)
+	delay := d.baseDelay
 	var lastErr error
```

### 2. Retry without backoff (errors.retry_without_backoff), Major, planted, notify/dispatcher.go lines 60 to 61

- Consequence: When the mail server fails transiently, all attempts fire at the baseDelay interval with no growth, so a struggling server gets hit at a fixed rate for the whole retry budget and a short outage can turn into a longer one.
- In an interview: The retry loop no longer doubles the delay between attempts, so backoff is flat rather than exponential. Restore the `delay *= 2` step after each wait so retries spread out and give the dependency room to recover.

Proven by the judge: The edit removes the 'delay *= 2' line, so every retry waits the same baseDelay instead of a doubling delay. The retry loop now fires at a fixed interval, which matches the claimed consequence of constant-rate retries hammering a struggling server. The original code doubles delay each attempt, so it does have backoff and lacks the defect. The attempt count is still bounded by maxAttempts, so the consequence is specifically the missing growth, which the edit introduces.


The fix, in notify/dispatcher.go:

```diff
 		}
+		delay *= 2
 	}
```

### 3. Leaked handle or connection (resources.leaked_handle), Minor, found in review, notify/dispatcher.go lines 56 to 60

- Consequence: When ctx is cancelled during backoff, the time.After timer is not stopped and stays allocated until the full delay elapses. Under heavy cancellation with long backoff delays, many pending timers can pile up, although the cost is bounded by the delay and Go 1.23+ collects unreferenced timers.
- In an interview: time.After cannot be cancelled, so when the context wins the select the timer keeps its resources until it fires. Creating a timer with time.NewTimer and calling Stop on the cancellation path releases it immediately.

Proven by the judge: A timer leak from time.After until it fires is a real, if minor, resource concern in a retry loop. It is not one of the planted issues and is a valid defect in the code as written.

The fix, in notify/dispatcher.go:

```diff
+		timer := time.NewTimer(delay)
 		select {
 		case <-ctx.Done():
+			timer.Stop()
 			return fmt.Errorf("sending to %s: %w", to, ctx.Err())
-		case <-time.After(delay):
+		case <-timer.C:
 		}
```

## The blind review

1. Critical in notify/dispatcher.go: The backoff is computed once, before the loop, as baseDelay shifted by maxAttempts, and never changes between attempts. The doc comment promises that backoff doubles after each attempt, but every retry waits the same large delay (and shifting by maxAttempts rather than attempt-1 is wrong). Compute the delay inside the loop, e.g. baseDelay << (attempt-1), and cap it so large maxAttempts cannot overflow or produce absurd waits.
   Quoted: delay := d.baseDelay << uint(d.maxAttempts)
   Judged: Matches { issues: [0, 1] }. Correctly identifies that the delay is fixed rather than doubling per attempt and that shifting by maxAttempts is wrong, and that large values can overflow. Matches both the overflow issue and the missing-backoff issue.
2. Minor in notify/dispatcher.go: time.After allocates a timer that is not released until it fires, even when ctx is cancelled first. Use time.NewTimer and Stop it, or otherwise avoid leaking timers in a retry loop.
   Quoted: case <-time.After(delay):
   Judged: ValidExtra. A timer leak from time.After until it fires is a real, if minor, resource concern in a retry loop. It is not one of the planted issues and is a valid defect in the code as written.
