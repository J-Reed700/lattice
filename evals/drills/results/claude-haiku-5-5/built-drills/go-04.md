43 | 	l.mu.Lock()
44 | 	defer l.mu.Unlock()
45 |

47 | 	now := l.now()

60 |

64 | 	}

## The key

### 1. Wrong operator or comparison (correctness.wrong_operator), Critical, planted, ratelimit/limiter.go lines 61 to 62

- Consequence: A bucket holding exactly one token is denied, so with burst 1 no request is ever allowed and a key with a full bucket is refused on its last token. Clients get 429s well before their configured limit.
- In an interview: The comparison should be >= 1 because a request needs one whole token, but > 1 requires two. Use >= so that a single available token admits the request, and keep the boundary test covering burst 1.

Proven by the judge: The edit changes the admission check from tokens >= 1 to tokens > 1. A bucket holding exactly one token is now denied, so with burst 1 a fresh bucket (tokens=1) is refused and a full bucket loses its last token to denial. This is a wrong comparison operator matching the claimed consequence. The original code uses >= 1, which is correct and does not have this problem.


The fix, in ratelimit/limiter.go:

```diff
-	if b.tokens > 1 {
+	if b.tokens >= 1 {
 		b.tokens--
```

### 2. Error context lost (errors.lost_context), Minor, planted, ratelimit/limiter.go lines 30 to 30

- Consequence: Callers using errors.Is(err, ErrInvalidConfig) stop matching, and the message no longer says which value was rejected, so misconfigured deployments are harder to diagnose.
- In an interview: Returning a fresh errors.New drops the sentinel identity and the reason, so callers cannot test for the cause. Return ErrInvalidConfig, or wrap it with fmt.Errorf using %w and the offending rate and burst values.

Proven by the judge: The edit replaces the sentinel ErrInvalidConfig with a fresh errors.New message, so errors.Is(err, ErrInvalidConfig) no longer matches. That is a real loss of identity, but the claimed consequence also mentions the message not saying which value was rejected; the new message is generic and equally uninformative about the value, and the original already did not name the rejected value. The defect pattern is error context lost: the sentinel's identity is discarded, which matches the lost-context pattern in the sense that callers cannot identify the failure. The original returns the sentinel directly with no wrapping, so it does not lack the identity; it has the full context available to callers. The edit introduces the lost-identity problem, which fits the pattern's consequence of callers being unable to tell what failed, so the edit introduces the defect while the original does not.


The fix, in ratelimit/limiter.go:

```diff
-		return nil, errors.New("ratelimit: invalid config")
+		return nil, ErrInvalidConfig
```

### 3. Lock held across a slow call (concurrency.lock_held_across_slow_call), Major, planted, ratelimit/limiter.go lines 43 to 47

- Consequence: Every Allow call for every key queues behind the sleep, so throughput collapses to about a thousand requests per second and latency spikes under load. If the injected clock or a hook ever blocks on I/O, the whole limiter stalls.
- In an interview: The mutex guards the bucket map and is held across a blocking call, so all callers serialize on that slow operation. Do the slow work outside the lock, or keep the critical section limited to bucket arithmetic.

Proven by the judge: The edit inserts time.Sleep(time.Millisecond) while l.mu is held inside Allow, so every Allow call for every key is serialized behind a 1ms sleep, which is a slow operation under the lock. The original Allow holds the lock only for in-memory map and arithmetic work, with no I/O or blocking call. The claimed consequence (throughput collapse to roughly a thousand requests per second, stalls from blocking hooks) follows directly from the sleep under the lock, so the edit introduces exactly the lock-held-across-slow-call pattern. The original code does not have it, since l.now is a time source and the test-only override does not block.


The fix, in ratelimit/limiter.go:

```diff
 	l.mu.Lock()
 	defer l.mu.Unlock()
 
-	time.Sleep(time.Millisecond)
 	now := l.now()
```

### 4. Unbounded growth (resources.unbounded_growth), Major, found in review, ratelimit/limiter.go lines 50 to 50

- Consequence: Every new key adds a bucket that is never removed except by Forget, so if keys come from client-controlled values such as headers or spoofed addresses, an attacker can send requests with fresh keys and grow the map until the process runs out of memory.
- In an interview: A map keyed by client-supplied data with no removal path is a memory-exhaustion vector, because the attacker controls how many keys exist. The fix caps the map size and evicts an entry before inserting a new one, which bounds memory at the cost of occasionally resetting a legitimate client's bucket; idle-time eviction is the better long-term design.

Proven by the judge: Unbounded bucket map growth from client-controlled keys is a real memory-exhaustion risk not present in the key, and the clean code shares it, so it is a genuine defect in the clean design too.

The fix, in ratelimit/limiter.go:

```diff
-b = &bucket{tokens: l.burst, last: now}
+const maxBuckets = 100000
+		if len(l.buckets) >= maxBuckets {
+			for k := range l.buckets {
+				delete(l.buckets, k)
+				break
+			}
+		}
+		b = &bucket{tokens: l.burst, last: now}
```

## The clean review

- Major: Retry-After is computed by truncating wait.Seconds() to an int. A wait of 1.5s becomes 1, so well-behaved clients retry before a token is available and get denied again. The value should round up, matching the ceiling used in Allow.
