## Overview

The Recall backend uses **Alembic** for database migrations with **PostgreSQL 15+** and **pgvector** extension. Migrations are versioned, sequential changes that evolve the database schema over time.

### Key Principles

1. **Every schema change requires a migration** - Never modify models without a migration
2. **Migrations must be reversible** - Always implement `downgrade()` when possible
3. **Test both directions** - Test `upgrade` and `downgrade` before production
4. **One change per migration** - Keep migrations focused and atomic
5. **Data safety first** - Never lose user data, even during rollback

### Migration Files Location

```
vault/backend/
├── migrations/
│   ├── versions/
│   │   ├── 001_initial.py
│   │   ├── 002_sync_tables.py
│   │   ├── 003_add_sync_state_and_soft_delete.py
│   │   └── ...
│   ├── env.py
│   └── script.py.mako
└── alembic.ini
```

## Migration Philosophy

### Simple > Complex

Follow the "Database Architect" philosophy:

- **Start simple**: Add fields as flexible types (TEXT/JSONB) initially
- **Evolve gradually**: Structure emerges from actual usage patterns
- **Measure first**: Add indexes only when metrics justify them
- **Trust the database**: Use PostgreSQL features (triggers, constraints) over app logic

### Reversible by Default

Every migration should be reversible unless it involves data transformation that cannot be undone:

```python
def upgrade() -> None:
    """Add new feature."""
    op.add_column('documents', sa.Column('new_field', sa.String(255)))

def downgrade() -> None:
    """Remove new feature."""
    op.drop_column('documents', 'new_field')
```

**Exception**: Data migrations that aggregate or transform data may not be fully reversible. Document this clearly:

```python
def downgrade() -> None:
    """Rollback is not fully reversible - aggregated data will be lost."""
    # Best-effort rollback
    pass
```

## Creating Migrations

### Auto-generate from Models

**Recommended approach** for schema changes:

```bash
cd vault/backend

# Activate Poetry environment
poetry shell

# Generate migration from model changes
alembic revision --autogenerate -m "add user preferences table"

# Review generated migration in migrations/versions/
# Edit as needed - auto-generation is not perfect!
```

**Always review auto-generated migrations** for:
- Unnecessary changes (e.g., comment modifications)
- Missing indexes
- Foreign key constraints
- Enum types (may need manual creation)

### Manual Migration Creation

For data migrations or complex changes:

```bash
alembic revision -m "migrate old format to new format"
```

Then implement `upgrade()` and `downgrade()` manually.

## Testing Migrations

### Pre-Production Testing Checklist

**Before deploying ANY migration to production:**

- [ ] Test on development database first
- [ ] Test both `upgrade` and `downgrade`
- [ ] Verify data integrity after migration
- [ ] Test application works with new schema
- [ ] Test application works after rollback
- [ ] Check migration performance with production-sized data
- [ ] Review SQL generated by migration
- [ ] Document any manual steps required

### Testing Process

#### 1. Test Upgrade on Development

```bash
cd vault/backend
poetry shell

# Backup development database first
pg_dump -U postgres -d recall_dev > backup_before_migration.sql

# Apply migration
alembic upgrade head

# Verify schema changes
psql -U postgres -d recall_dev -c "\d+ documents"

# Run application tests
pytest tests/ -v

# Check application still works
poetry run uvicorn src.main:app --reload
```

#### 2. Test Rollback

```bash
# Rollback the migration
alembic downgrade -1

# Verify schema reverted
psql -U postgres -d recall_dev -c "\d+ documents"

# Run tests again
pytest tests/ -v

# Check application still works (with old schema)
poetry run uvicorn src.main:app --reload
```

#### 3. Re-apply and Continue

```bash
# Re-apply the migration
alembic upgrade head

# Verify everything still works
pytest tests/ -v
```

### Testing with Production-Sized Data

```bash
# Create test database with production data snapshot
pg_restore -U postgres -d recall_test production_snapshot.dump

# Test migration on production-sized data
alembic -c alembic_test.ini upgrade head

# Measure migration time
time alembic -c alembic_test.ini upgrade head

# If migration takes >30 seconds, consider:
# - Running it during maintenance window
# - Splitting into smaller migrations
# - Adding indexes CONCURRENTLY
```

## Rollback Procedures

### When to Rollback

Rollback a migration if:

- Application crashes after deployment
- Migration caused data corruption
- Performance degraded unacceptably
- Migration took too long and needs to be rescheduled
- Critical bug discovered in migration logic

### Standard Rollback Procedure

#### Step 1: Assess the Situation

```bash
# Check current migration version
alembic current

# Check migration history
alembic history --verbose

# Identify problematic migration
# Example output:
# 003_add_sync_state (head) <- CURRENT
# 002_sync_tables
# 001_initial
```

#### Step 2: Stop Application Traffic

```bash
# Stop backend services
docker-compose down

# Or scale to zero
kubectl scale deployment recall-backend --replicas=0
```

#### Step 3: Backup Database

```bash
# CRITICAL: Always backup before rollback
pg_dump -U postgres -d recall_prod > backup_before_rollback_$(date +%Y%m%d_%H%M%S).sql

# Verify backup was created
ls -lh backup_before_rollback_*.sql
```

#### Step 4: Execute Rollback

```bash
# Rollback one migration
alembic downgrade -1

# Or rollback to specific version
alembic downgrade 002_sync_tables

# Verify rollback succeeded
alembic current
```

#### Step 5: Verify Data Integrity

```bash
# Check critical tables
psql -U postgres -d recall_prod -c "SELECT COUNT(*) FROM documents;"
psql -U postgres -d recall_prod -c "SELECT COUNT(*) FROM users;"

# Run integrity checks
python scripts/verify_database_integrity.py
```

#### Step 6: Restart Application

```bash
# Restart services with previous code version
git checkout <previous-tag>
docker-compose up -d

# Or restore Kubernetes deployment
kubectl rollout undo deployment recall-backend
```

### Partial Rollback (Data Migration)

If migration included data transformation:

```python
def downgrade() -> None:
    """Partial rollback - cannot restore transformed data.
    
    WARNING: This rollback will:
    - Restore schema to previous state
    - Preserve original data in backup column
    - New data created during migration will be lost
    """
    # Restore schema
    op.drop_column('documents', 'new_format_field')
    
    # Original data is preserved in 'old_format_field_backup'
    op.execute("""
        UPDATE documents 
        SET old_format_field = old_format_field_backup 
        WHERE old_format_field_backup IS NOT NULL
    """)
    
    op.drop_column('documents', 'old_format_field_backup')
```

## Production Deployment

### Pre-Deployment Checklist

- [ ] Migration tested on development
- [ ] Migration tested with production-sized data
- [ ] Rollback tested and verified
- [ ] Backup procedures documented
- [ ] Downtime window scheduled (if needed)
- [ ] Team notified
- [ ] Rollback plan reviewed
- [ ] Database backup scheduled before migration

### Zero-Downtime Migration Strategy

For migrations that can run while application is live:

```python
def upgrade() -> None:
    """Add column with default - zero downtime.
    
    This migration:
    1. Adds column with default value (instant in PostgreSQL 11+)
    2. Creates index CONCURRENTLY (doesn't block writes)
    3. Application can run during migration
    """
    # Add column with default (fast in PostgreSQL 11+)
    op.add_column(
        'documents',
        sa.Column('new_field', sa.String(255), 
                  nullable=False, 
                  server_default='default_value')
    )
    
    # Create index without blocking writes
    op.create_index(
        'ix_documents_new_field',
        'documents',
        ['new_field'],
        postgresql_concurrently=True
    )
```

**Note**: When using `postgresql_concurrently=True`, you must run Alembic with:

```bash
# Disable transaction for CONCURRENT operations
alembic upgrade head --sql > migration.sql
psql -U postgres -d recall_prod -f migration.sql
```

### High-Risk Migration Strategy

For migrations that require downtime:

1. **Schedule maintenance window**
   ```bash
   # Example: Friday 2AM - 4AM
   echo "Maintenance window: Friday 2AM - 4AM UTC"
   ```

2. **Enable maintenance mode**
   ```bash
   # Return 503 for all requests
   kubectl set env deployment/recall-backend MAINTENANCE_MODE=true
   ```

3. **Backup database**
   ```bash
   pg_dump -U postgres -d recall_prod -F c > backup_pre_migration.dump
   ```

4. **Run migration**
   ```bash
   alembic upgrade head
   ```

5. **Verify and resume**
   ```bash
   # Run smoke tests
   pytest tests/smoke/ -v
   
   # Disable maintenance mode
   kubectl set env deployment/recall-backend MAINTENANCE_MODE=false
   ```

## Emergency Procedures

### Emergency Rollback Procedure

If production is down due to bad migration:

```bash
# 1. IMMEDIATE: Stop all traffic
kubectl scale deployment recall-backend --replicas=0

# 2. Rollback database (should take <30 seconds)
alembic downgrade -1

# 3. Rollback application code
kubectl rollout undo deployment recall-backend

# 4. Restore traffic
kubectl scale deployment recall-backend --replicas=3

# 5. Verify system health
curl https://api.recall.app/health
```

### If Rollback Fails

```bash
# 1. Restore from backup
pg_restore -U postgres -d recall_prod --clean backup_before_migration.dump

# 2. Verify restoration
psql -U postgres -d recall_prod -c "SELECT COUNT(*) FROM documents;"

# 3. Check Alembic version table
psql -U postgres -d recall_prod -c "SELECT * FROM alembic_version;"

# 4. If alembic_version is wrong, manually fix it
psql -U postgres -d recall_prod -c "UPDATE alembic_version SET version_num = '002_sync_tables';"

# 5. Restart application
kubectl rollout restart deployment recall-backend
```

### Data Corruption Recovery

If data corruption detected:

```bash
# 1. Stop application immediately
kubectl scale deployment recall-backend --replicas=0

# 2. Assess corruption scope
python scripts/assess_corruption.py

# 3. If minor: Fix with SQL
psql -U postgres -d recall_prod -f fix_corruption.sql

# 4. If major: Restore from backup
pg_restore -U postgres -d recall_prod --clean backup_latest.dump

# 5. Re-sync affected users
python scripts/trigger_resync.py --affected-users affected_users.txt
```

## Best Practices

### DO

✅ **Always backup before migrations**
```bash
pg_dump -U postgres -d recall_prod > backup_$(date +%Y%m%d_%H%M%S).sql
```

✅ **Test both upgrade and downgrade**
```bash
alembic upgrade head && alembic downgrade -1 && alembic upgrade head
```

✅ **Use transactions for safety**
```python
def upgrade() -> None:
    """Migration runs in transaction by default."""
    op.add_column('documents', sa.Column('new_field', sa.String()))
    # If this fails, entire migration rolls back
```

✅ **Add indexes CONCURRENTLY for large tables**
```python
op.create_index('ix_name', 'table', ['column'], postgresql_concurrently=True)
```

✅ **Document irreversible changes**
```python
def downgrade() -> None:
    """WARNING: This rollback loses aggregated statistics."""
    op.drop_table('aggregated_stats')
```

✅ **Use server defaults for NOT NULL columns**
```python
op.add_column('documents', 
    sa.Column('new_field', sa.String(), 
              nullable=False, 
              server_default='default'))
```

### DON'T

❌ **Don't modify existing migrations**
```bash
# NEVER do this:
git commit --amend migrations/versions/003_xxx.py

# Instead, create a new migration:
alembic revision -m "fix issue from migration 003"
```

❌ **Don't skip testing rollback**
```bash
# ALWAYS test rollback before production:
alembic upgrade head
alembic downgrade -1  # Test this!
alembic upgrade head
```

❌ **Don't add NOT NULL without default on large tables**
```python
# BAD: Will lock table while setting values
op.add_column('documents', sa.Column('new_field', sa.String(), nullable=False))

# GOOD: Add with default, then remove default in next migration
op.add_column('documents', sa.Column('new_field', sa.String(), 
              nullable=False, server_default='temp'))
```

❌ **Don't combine schema and data migrations**
```python
# BAD: Mixing schema and data changes
def upgrade():
    op.add_column('documents', sa.Column('migrated', sa.Boolean()))
    op.execute("UPDATE documents SET migrated = true WHERE ...")

# GOOD: Separate migrations
# Migration 1: Add column
# Migration 2: Migrate data
```

❌ **Don't drop columns immediately**
```python
# BAD: Dropping column immediately
def upgrade():
    op.drop_column('documents', 'old_field')

# GOOD: Multi-step deprecation
# Migration 1: Stop using column in application
# Migration 2: Wait 1-2 releases
# Migration 3: Drop column
```

## Common Scenarios

### Scenario 1: Adding a New Field

```python
def upgrade() -> None:
    """Add analytics_enabled field to users."""
    op.add_column(
        'users',
        sa.Column('analytics_enabled', sa.Boolean(), 
                  nullable=False, 
                  server_default='true')
    )

def downgrade() -> None:
    """Remove analytics_enabled field."""
    op.drop_column('users', 'analytics_enabled')
```

### Scenario 2: Adding an Index

```python
def upgrade() -> None:
    """Add index on documents.modified_at for faster queries."""
    # Use CONCURRENTLY to avoid locking table
    op.create_index(
        'ix_documents_modified_at',
        'documents',
        ['modified_at'],
        postgresql_concurrently=True
    )

def downgrade() -> None:
    """Remove index on documents.modified_at."""
    op.drop_index('ix_documents_modified_at', 'documents')
```

### Scenario 3: Renaming a Column

```python
def upgrade() -> None:
    """Rename content_text to content for clarity.
    
    Safe to run while application is live:
    - Old code uses content_text (still exists)
    - New code uses content (alias created)
    - Next release removes content_text
    """
    # Step 1: Add new column
    op.add_column('documents', sa.Column('content', sa.Text()))
    
    # Step 2: Copy data
    op.execute("UPDATE documents SET content = content_text")
    
    # Step 3: Make new column NOT NULL
    op.alter_column('documents', 'content', nullable=False)
    
    # DON'T drop old column yet - do in next migration

def downgrade() -> None:
    """Revert content column addition."""
    op.drop_column('documents', 'content')
```

### Scenario 4: Creating a New Table

```python
def upgrade() -> None:
    """Create analytics_events table for tracking."""
    op.create_table(
        'analytics_events',
        sa.Column('id', sa.Integer(), primary_key=True),
        sa.Column('user_id', sa.Integer(), sa.ForeignKey('users.id')),
        sa.Column('event_type', sa.String(100), nullable=False),
        sa.Column('event_data', postgresql.JSONB(), nullable=True),
        sa.Column('created_at', sa.DateTime(), nullable=False),
    )
    
    op.create_index('ix_analytics_events_user_id', 'analytics_events', ['user_id'])
    op.create_index('ix_analytics_events_created_at', 'analytics_events', ['created_at'])

def downgrade() -> None:
    """Drop analytics_events table.
    
    WARNING: All analytics events will be lost.
    """
    op.drop_index('ix_analytics_events_created_at', 'analytics_events')
    op.drop_index('ix_analytics_events_user_id', 'analytics_events')
    op.drop_table('analytics_events')
```

### Scenario 5: Data Migration

```python
def upgrade() -> None:
    """Migrate old status codes to new enum values.
    
    Maps:
    - 0 -> pending
    - 1 -> active
    - 2 -> completed
    """
    # Step 1: Add new column
    op.add_column(
        'documents',
        sa.Column('status_new', sa.String(20), nullable=True)
    )
    
    # Step 2: Migrate data
    op.execute("""
        UPDATE documents 
        SET status_new = CASE status_old
            WHEN 0 THEN 'pending'
            WHEN 1 THEN 'active'
            WHEN 2 THEN 'completed'
            ELSE 'unknown'
        END
    """)
    
    # Step 3: Make new column NOT NULL
    op.alter_column('documents', 'status_new', nullable=False)
    
    # Step 4: Rename columns
    op.alter_column('documents', 'status_old', new_column_name='status_old_backup')
    op.alter_column('documents', 'status_new', new_column_name='status')

def downgrade() -> None:
    """Revert status migration - partial data loss.
    
    WARNING: Status values created after migration cannot be mapped back.
    """
    # Restore old column
    op.alter_column('documents', 'status', new_column_name='status_new')
    op.alter_column('documents', 'status_old_backup', new_column_name='status_old')
    
    # Best effort: Map back
    op.execute("""
        UPDATE documents 
        SET status_old = CASE status_new
            WHEN 'pending' THEN 0
            WHEN 'active' THEN 1
            WHEN 'completed' THEN 2
            ELSE -1
        END
    """)
    
    # Drop new column
    op.drop_column('documents', 'status_new')
```

## Troubleshooting

### "ERROR: cannot execute XXX in a read-only transaction"

**Cause**: Trying to run migration on read replica

**Solution**:
```bash
# Connect to primary database
export DATABASE_URL="postgresql://user:pass@primary-db:5432/recall"
alembic upgrade head
```

### "ERROR: column 'xxx' already exists"

**Cause**: Migration already partially applied

**Solution**:
```bash
# Check what actually exists in database
psql -U postgres -d recall_prod -c "\d+ documents"

# Manually update alembic version if needed
psql -U postgres -d recall_prod -c "UPDATE alembic_version SET version_num = '002_sync_tables';"

# Then retry
alembic upgrade head
```

### "ERROR: relation 'xxx' does not exist"

**Cause**: Database and Alembic out of sync

**Solution**:
```bash
# Stamp database with current model state
alembic stamp head

# Then run migrations normally
alembic upgrade head
```
