# ADR-001: Use HNSW for Vector Similarity Search

## Status

**Accepted** - Implemented in Phase 1 (2025-11-15)

## Context

The Recall desktop application requires efficient Approximate Nearest Neighbor (ANN) search to find semantically similar documents based on vector embeddings. Key requirements include:

- **Performance**: Sub-100ms search latency for typical queries (top-k=10) on collections up to 100,000 documents
- **Memory efficiency**: Ability to run on consumer hardware with 8GB RAM
- **Local-first**: Must work entirely offline without external dependencies
- **Rust native**: Should integrate well with the Tauri Rust backend
- **Incremental updates**: Support adding/removing documents without full index rebuild

Vector embeddings are 384-dimensional float32 vectors generated by the `all-MiniLM-L6-v2` ONNX model.

## Decision

We will use **HNSW (Hierarchical Navigable Small World)** graphs via the `instant-distance` Rust crate for vector similarity search.

### Implementation Details

- **Crate**: `instant-distance` v0.7.0 with `"hnsw"` feature
- **Index parameters**:
  - `M = 16`: Number of bi-directional links per node (balance between recall and memory)
  - `ef_construction = 200`: Size of dynamic candidate list during construction (quality vs speed tradeoff)
  - `ef_search = 50`: Size of dynamic candidate list during search (adjustable per query)
- **Distance metric**: Cosine similarity (converted to distance via `1.0 - cosine_similarity`)
- **Persistence**: Serialized index saved to SQLite BLOB column for persistence across restarts
- **Concurrency**: Read-only search operations are thread-safe; writes require exclusive lock

### Code Structure

```rust
// search/hnsw_index.rs
pub struct HNSWIndex {
    index: instant_distance::HnswMap<Embedding, String>,  // Vector -> Document ID
    params: HnswParams,
}

impl HNSWIndex {
    pub fn search(&self, query: &Embedding, k: usize) -> Vec<SearchResult> {
        self.index.search(query, &SearchParams { ef: 50 })
            .take(k)
            .map(|item| SearchResult {
                document_id: item.value.clone(),
                score: 1.0 - item.distance,  // Convert distance to similarity
            })
            .collect()
    }
}
```

## Consequences

### Positive

1. **Excellent query performance**: O(log N) average case search complexity with high recall (>95% for typical parameters)
2. **Proven algorithm**: HNSW is state-of-the-art for ANN search, widely used in production (Qdrant, Milvus, Weaviate)
3. **Rust native**: `instant-distance` is a pure Rust implementation with zero-copy operations
4. **Tunable tradeoffs**: Can adjust `M`, `ef_construction`, and `ef_search` to balance speed, memory, and accuracy
5. **Incremental updates**: Supports inserting new vectors without full rebuild (though less efficient than batch build)

### Negative

1. **High memory overhead**: HNSW stores multiple links per node (~96 bytes per vector for M=16)
   - **Impact**: 100K documents = ~40MB index + ~150MB vectors = ~190MB total
2. **Slower indexing**: Building HNSW is slower than simpler structures like flat or IVF
   - **Impact**: ~500ms for 1000 documents on M1 MacBook Pro
3. **Delete complexity**: Removing vectors requires marking as deleted and periodic compaction
4. **No GPU acceleration**: Unlike FAISS, instant-distance is CPU-only
5. **Limited configurability**: Fewer tuning options compared to FAISS

### Neutral

- **Trade recall for speed**: Lower `ef_search` values reduce latency but may miss some relevant results
- **Cold start cost**: Loading serialized index from disk takes ~100-200ms for 100K documents

## Alternatives Considered

### 1. FAISS (Facebook AI Similarity Search)

**Pros**:
- Industry standard with extensive optimizations
- GPU acceleration available
- Multiple index types (Flat, IVF, PQ, HNSW)
- Highly optimized C++ implementation

**Cons**:
- **Rejected**: Complex C++ dependency, difficult to cross-compile for multiple platforms
- Requires FFI bindings or separate process communication
- Larger binary size impact (~50MB+)
- Overkill for local desktop use case

### 2. Annoy (Approximate Nearest Neighbors Oh Yeah)

**Pros**:
- Simple tree-based algorithm
- Memory-mapped index for fast loading
- Smaller memory footprint than HNSW

**Cons**:
- **Rejected**: Lower recall than HNSW at same speed
- No pure Rust implementation (would need C++ FFI)
- Immutable index (rebuilds required for updates)
- Slower query time for high-dimensional data

### 3. Ball Tree / KD-Tree (via `kiddo` crate)

**Pros**:
- Simple, well-understood algorithms
- Exact nearest neighbor search
- Native Rust implementations available

**Cons**:
- **Rejected**: Poor performance in high dimensions (curse of dimensionality)
- Query time degrades to O(N) for 384 dimensions
- Not suitable for approximate search

### 4. Brute Force Flat Index

**Pros**:
- Simplest implementation (dot product + sort)
- 100% recall guaranteed
- No index build time
- Minimal memory overhead

**Cons**:
- **Rejected**: O(N) query time becomes prohibitive above ~10K documents
- Would need <50ms for 10K documents, achievable on modern CPUs but doesn't scale

### 5. Product Quantization (PQ)

**Pros**:
- Extreme memory compression (32x smaller than full vectors)
- Suitable for very large collections (millions of vectors)

**Cons**:
- **Rejected**: Adds complexity without clear benefit for target scale (100K documents)
- Reduced accuracy from lossy compression
- No production-ready Rust implementation

## Performance Benchmarks

Based on initial testing with 10,000 documents (384-dim vectors):

| Operation | HNSW (instant-distance) | Flat Index |
|-----------|------------------------|------------|
| Index build | ~500ms | 0ms |
| Search (k=10) | ~2ms | ~8ms |
| Memory | ~19MB | ~15MB |
| Recall@10 | 96% | 100% |

**Scaling expectations** (extrapolated):
- 100K docs: ~5ms search, ~190MB memory
- 1M docs: ~8ms search, ~1.9GB memory (would need optimization)

## Implementation Notes

### Serialization Strategy

The HNSW index is serialized using `bincode` and stored in SQLite:

```sql
CREATE TABLE vector_index (
    id INTEGER PRIMARY KEY,
    version INTEGER NOT NULL,
    params_json TEXT NOT NULL,
    index_data BLOB NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Incremental Updates

For adding new documents:
1. Deserialize existing index from SQLite
2. Insert new vectors: `index.insert(embedding, doc_id)`
3. Serialize and save updated index

For deletions (lazy approach):
1. Maintain a separate `deleted_documents` set
2. Filter out deleted IDs from search results
3. Rebuild index periodically when deleted ratio >20%

### Future Optimizations

If performance becomes an issue at scale:
1. **Hybrid approach**: Use HNSW for large collections (>1K), flat index for small ones
2. **Quantization**: Store compressed vectors, expand only for final ranking
3. **Disk-based index**: Memory-map HNSW graph for huge collections
4. **Multi-index**: Shard by document type or collection
