## The key

### 1. Off-by-one error (correctness.off_by_one), Major, planted, inventory/reservation.go lines 79 to 79

- Consequence: A reservation that exactly matches the remaining available stock is rejected as insufficient, so the last unit of a SKU can never be held and customers see false out-of-stock results.
- In an interview: The check uses a strict comparison where it should allow an exact fit, so the boundary is off by one. Stock should be reservable up to and including the available count, so the comparison should be '<' as it was before.

Proven by the judge: The edit changes the reservation check from rejecting only when available < qty to rejecting when available <= qty. This means a request exactly matching remaining available stock is now rejected, so the last unit can never be held, matching the claimed consequence. The original code has the correct strict comparison and does not have this problem. The edit introduces exactly this off-by-one boundary defect. The existing tests do not cover the exact-match case, but the defect itself is the claimed one.


The fix, in inventory/reservation.go:

```diff
-	if s.onHand[sku]-s.heldLocked(sku) <= qty {
+	if s.onHand[sku]-s.heldLocked(sku) < qty {
```

### 2. Error reported as success (errors.error_as_success), Critical, planted, inventory/reservation.go lines 98 to 99

- Consequence: Committing a lapsed or unknown hold reports success without decrementing stock, so the caller believes an order is fulfilled when no stock was consumed and the hold was never honoured.
- In an interview: When the hold is missing or expired, Commit now returns nil instead of an error, so the caller cannot tell the commit failed. The fix is to keep returning the 'no live reservation' error so the caller re-reserves.

Proven by the judge: The edit changes Commit so that when the hold is missing or lapsed it returns nil instead of an error. The claimed consequence is that callers believe the order is fulfilled when no stock was consumed. That is exactly the error-as-success pattern: the failure is converted into a success status. The original code returns an error for this case, so it does not have the problem. The edit introduces it. The existing test TestExpiredHoldReleasesStock would now fail, but that is a consequence of the same defect, not a separate one.


The fix, in inventory/reservation.go:

```diff
 		delete(s.reservations, id)
-		return nil
+		return fmt.Errorf("commit %q: no live reservation", id)
```

### 3. Unsynchronised shared state (concurrency.unsynchronised_shared_state), Major, planted, inventory/reservation.go lines 41 to 41

- Consequence: Concurrent Restock calls and Available or Reserve calls race on the onHand map, causing lost increments or a Go fatal 'concurrent map read and map write' crash under load.
- In an interview: Restock updates the shared onHand map without taking the store mutex that guards it, so writes race with other goroutines. Restore the Lock/Unlock pair so every access to onHand is serialised.

Proven by the judge: The edit removes the mutex lock/unlock from Restock, so the onHand map write is no longer guarded. Concurrent Restock calls now race with Available/Reserve/Commit, which hold s.mu while reading onHand. This introduces unsynchronised shared map access that can cause a Go 'concurrent map read and map write' fatal error or lost updates. In the original code, Restock held the lock, so all onHand accesses were synchronised and the problem was absent.


The fix, in inventory/reservation.go:

```diff
+	s.mu.Lock()
+	defer s.mu.Unlock()
 	s.onHand[sku] += qty
```

## The clean review

- Major: Reserve checks for an existing reservation id before heldLocked reclaims expired holds. If a hold with the same id has lapsed but not yet been swept, Reserve wrongly returns 'already exists' instead of allowing the id to be reused.
- Nit: The Available doc comment says reads never write, but heldLocked deletes expired reservations, so Available does mutate the map. The comment is misleading.

## The blind review

1. Critical in inventory/reservation.go: Commit returns nil both when the hold is missing and when it has lapsed. The doc comment says a lapsed hold is 'reported as missing so the caller re-reserves', but a nil return reports success, so the caller cannot tell the commit failed and may treat the sale as completed. Return an error (e.g. a sentinel ErrHoldNotFound/ErrHoldExpired) in both cases. The existing test already expects an error here, so this also makes it fail.
   Quoted: if !ok || !s.now().Before(r.ExpiresAt) {
   Judged: Matches { issues: [1] }. Correctly identifies that Commit returns nil for missing or lapsed holds, reporting false success.
2. Major in inventory/reservation.go: Restock modifies onHand without acquiring s.mu, unlike every other method. Concurrent Restock and Reserve/Available calls race on the map, which can crash the program with a concurrent map write. Take the lock as the other methods do.
   Quoted: s.onHand[sku] += qty
   Judged: Matches { issues: [2] }. Correctly identifies the unlocked onHand write in Restock causing data races and map crashes.
3. Major in inventory/reservation.go: The comparison uses <= so a reservation that exactly consumes the remaining stock is rejected as insufficient. Stock of 3 with a request for 3 should succeed. This should be '<'.
   Quoted: if s.onHand[sku]-s.heldLocked(sku) <= qty {
   Judged: Matches { issues: [0] }. Correctly identifies that <= should be < so exact-fit reservations are allowed.
4. Nit in inventory/reservation.go: heldLocked is called here purely for its side effect, and then called again on the next line, which repeats the full scan. The first call is redundant: the availability check already reclaims expired holds. Remove it, or make the reclaim explicit and call it once.
   Quoted: s.heldLocked(sku) // reclaim expired holds first
   Judged: FalsePositive. The redundant first heldLocked call is a style and efficiency remark about duplicate scanning, not a defect that causes harm; the clean code has the same call.
5. Major in inventory/reservation_test.go: The insufficient-stock test only covers a request larger than stock. It does not cover the exact-fit boundary, which the <= bug breaks. Add a case where the request equals available stock and expect success.
   Quoted: err := s.Reserve("r1", "sku-1", 2, time.Minute)
   Judged: Matches { issues: [0] }. Notes that the test lacks an exact-fit boundary case, which is the scenario broken by the off-by-one on line 79, so it is about issue 2 even though it blames the test gap rather than the comparison.
6. Minor in inventory/reservation_test.go: The test passes only if Commit returns an error for an expired hold, which is the intended behaviour. It also needs to assert that on-hand stock is unchanged after the failed commit. Add that check, and ideally an equivalent check for a missing id.
   Quoted: if err := s.Commit("r1"); err == nil {
   Judged: FalsePositive. Suggests asserting unchanged stock after a failed commit; this is a test-coverage preference and does not describe a defect in the code.

- planted-1 (correctness.off_by_one): the review Found { finding: 2 }. Finding 3 names the off-by-one cause: the <= comparison rejects a reservation that exactly consumes remaining stock, so the last unit can never be held.
